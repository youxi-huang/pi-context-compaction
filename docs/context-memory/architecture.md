# Architecture

The original session JSONL is the history store. A checkpoint contains a structured note plus source identifiers and a branch snapshot. Original records remain available through a bounded history API.

## Runtime modules

| Module | Responsibility |
| --- | --- |
| `config.ts` | Process-latched enable flag, writer selection (`session` or a fixed `provider/model`), kept-context, note and compaction-point budgets. |
| `loader.ts`, `extension.ts`, `policy.ts` | Resident loading, tools, ownership, handler ordering and competing-compactor rejection. |
| `controller.ts` | Freeze source, choose the cut, invoke writer, validate candidate and block requests after failure. |
| `writer.ts`, `notes.ts` | Session writer over the current provider prefix, fixed writer over raw-source chunks, structured notes, quotation/citation checks and accumulated usage. |
| `history.ts`, `grant-file.ts` | Snapshots, bounded search/read, child identity and revocation. |
| `lease.ts`, `storage.ts` | Process identity, writer ownership, atomic first publication and append rollback. |
| `events.ts` | Local append-only evaluation log: outcomes, error classes, durations and counts, with per-session quotas and no content. |
| `identity.ts`, `build.ts`, `index.ts` | Format identity, source fingerprint and public integration surface. |

## Host changes

The SDK wraps resource loaders so ordinary filtering cannot remove the resident. Runtime construction checks ownership and tools. The extension runner propagates request-blocking failures from the resident instead of swallowing them. For `session_before_compact` it runs other extensions first and the resident last; a non-resident handler may observe the event and return `undefined`, but any returned compaction or cancellation is rejected before the writer runs.

`SessionManager` calls storage before publishing candidate entries to its in-memory tree. This includes first flush and subsequent writes. Session opening, branching and forking acquire a destination lease before exposing writable state. Extension events alone run too late to enforce these boundaries.

The controller returns a compaction candidate to Pi's existing commit path. It does not append checkpoints or replace agent messages itself. Storage checks the source snapshot again at commit. Cancellation, changed sources and disk failures leave the candidate uncommitted. Failed compaction blocks the next provider request until explicit retry or new input.

Each attempt the resident starts is settled exactly once in the event log: on `session_compact` as committed, or on `session_compact_failed` as failed or aborted with the error class recorded by the controller. A failure reported by Pi without a resident attempt is logged only when it carries one of the extension's own error classes, such as a competing compactor; host refusals like "nothing to compact" are not attempts. Every guard rejection is logged except repeated `CONTEXT_BLOCKED` within one failure, which is logged once. Logging never changes compaction behavior; a log write error is shown by `/compaction-status` and otherwise ignored.

Writer accounting is collected before note validation: `writerCalls` counts started calls and `usageReports` counts returned usage records, including an invalid note or cancellation after the response. Usage is accumulated once across fixed-writer chunks. Calls without a returned usage record have unknown cost. `writerMs` also survives writer failure. The report's existing `tokens` fields retain their committed-compaction meaning; JSON budget occupancy now uses `noteJsonBytes / (noteBudget × 3)` rather than dividing rendered-note tokens by a JSON budget, and legacy events without byte measurements are counted as unknown; `writerAttempts.all` and `writerAttempts.byOutcome` add known usage across all outcomes, unreported calls and legacy attempts without call counts. A malformed JSON note is `CONTEXT_NOTE_INVALID`, without copying its text into the error.

## Notes and retrieval

Two writers exist and neither substitutes for the other. The default `session` writer sends the session model its own next provider request, meaning the current system prompt, active tool definitions and converted messages in the same order Pi would send them, followed by one closing user message that carries the note schema, the rules, the previous note, increment candidates, bounded excerpts of referenced originals and a manifest mapping each uncovered entry to its ID with its opening words. The manifest exists because entry IDs are not visible inside the conversation; it shrinks to IDs only when the window is tight, and the request fails with `CONTEXT_WRITER_CAPACITY` rather than dropping the prefix. The prefix is rebuilt the way the resident's own `context` handler shapes it, including the pending-notes message, and drops a trailing failed assistant message the way overflow recovery does; other extensions' `context` handlers are not replayed, so an extension that rewrites the context on every request also defeats the provider's prompt cache. Prefix size is estimated with Pi's message estimator, so images count at their flat estimate rather than as base64 text. A fixed writer must exist in the catalog and its provider must have configured authentication; either failure is `CONTEXT_WRITER_UNAVAILABLE`. A fixed `provider/model` writer instead receives the previous note, new original records in sequential chunks and bounded excerpts of referenced originals. The session writer reasons at the session's current thinking level, mirroring Pi's own summarizer; `writerEffort` applies to a fixed writer only, and no effort is sent to a model without declared reasoning support. The effort actually sent is recorded in the compaction event as `writerEffort`. Increment notes are unverified candidates. The handover-writing request is explicitly internal control for this response only, not a user ruling: it neither completes/cancels the task nor changes permissions, and must not appear in the note as a new restriction or gap. Every quote must appear verbatim in a cited record; every source must be on the selected branch. These checks establish reference consistency, not semantic completeness.

The controller chooses the cut itself instead of adopting Pi's `keepRecentTokens` cut. With the default budget of zero, nothing is kept once the last turn is complete and the checkpoint's `firstKeptEntryId` is the sentinel `context-memory:keep-none`, which Pi's context assembly already treats as "no kept entries"; the next request holds the system prompt, the note and the new input. An unfinished turn, or an overflow retry, keeps from its own user message so tool calls and results stay paired. If no new user turn has started since the checkpoint, that message may be inside its kept prefix; repeated compaction follows the stored `firstKeptEntryId` to find it. Once a new user turn exists, a positive budget stays after the previous checkpoint, as before. A session smaller than the budget keeps its latest turn. Context assembly omits older compaction entries that lie inside a retained turn, leaving one current summary plus complete tool rounds. Those checkpoints and original records remain on disk, and `priorCheckpoints` remains in the current summary. Storage accepts the sentinel; every other `firstKeptEntryId` must exist on the branch. Pi's `findCutPoint` also falls back to the latest cut point instead of the first when the budget is met inside the trailing entries of the last turn, so a branch ending in a tool result still prepares a compaction.

The compaction threshold is `min(model cap, 0.8 × context window, context window − output reserve, compactAt)`. Caps are 400,000 for GPT and 200,000 for Gemini; other families have no extra cap. The final input allowance is separately `context window − output reserve`, including the serialized-payload check. The threshold is a preferred trigger, not the input allowance: using it for both could reject a request before the host's different token estimate reached the trigger. Estimates are conservative approximations, not billing measurements.

### Tiered note budgets and bounded repair (v0.2.3)

The controller freezes a note budget after selecting the cut and before any writer call. It measures readable source text in the intersection of active context entries and entries before the cut, using `ceil(UTF-8 bytes / 3)` per entry. It excludes archived checkpoints, already removed history, kept originals and excluded shell output. System prompts and tool definitions are not source entries; image data and hidden reasoning payloads are replaced by the existing source-text markers, not counted as base64. This is a reproducible size proxy, not a semantic information-density estimate or provider token count.

| Released source estimate | Base allowance | Hard allowance |
| --- | ---: | ---: |
| Up to 80,000 | 3,000 | 4,000 |
| 80,001–200,000 | 4,000 | 5,000 |
| 200,001–400,000 | 5,000 | 6,000 |
| Above 400,000 | 6,000 | 8,000 |

In tiered mode, the base is also at least 90% (rounded up) of the preceding note's actual JSON estimate, and the hard allowance at least that note's actual estimate. This avoids abrupt shrinking without inheriting a lifetime high-water tier: when the writer produces a smaller note, the next floor falls with it. Both allowances are capped at 8,000 and at 15% of the trigger with a floor of 500. Capacity caps take precedence over the previous-note floor. The trigger itself is unchanged; the highest tier is not a recommendation to postpone automatic compaction near a 1M window.

Explicit `noteTokens` selects fixed mode: base and hard allowances both equal the configured count after capacity and storage caps. It is not reinterpreted as a soft target. Omitting it selects tiered mode. The existing `context_note` increment limit remains 2,000, and pending-candidate prefix injection keeps its stable allowance (normally 3,000), independent of the cut-dependent writer budget. This avoids a budget change silently changing the reused provider prefix.

The validator measures `JSON.stringify(note)` in UTF-8 bytes, including keys, quotes and source IDs. Writer instructions state the base and hard byte limits and aim for 75% of the base. A valid candidate above the base but within the hard limit commits without another call; the event records elastic usage. Budgets never grow in response to model output. Host continuation and checkpoint lineage remain separately measured and consume the final recovery allowance.

Both `sources` and `supersedes` IDs must resolve to readable entries in the supplied branch. Checkpoints, metadata, empty text and unavailable entries are rejected. A superseded older ruling does not have to be duplicated in the current fact's `sources`; the two fields share validation rules, not identical membership. The same check runs on note commit and persisted-checkpoint reopening. Older notes that contain unreadable supersedes fail explicitly; original history is retained and no silent migration or repair is applied.

With `noteRepair: true` (default), only a schema-, source- and quote-valid candidate over the hard limit is eligible for one same-model size repair across the entire compaction, not one per fixed-writer chunk. Missing continuation steps are ineligible. The repair request contains the candidate, measured size, bounded original excerpts, complete verified quotations and active requests; it does not replay the session prefix. Its complete input plus output reserve must fit both the writer window and a 64,000-token repair-request ceiling. No tools, model substitution or transport retries are allowed. All source IDs, supersedes IDs, exact quotations and occupied sections (including unresolved gaps) must survive the repair; the repaired note is validated against the frozen original branch again. These are structural protections, not proof of semantic completeness. Missing or distorted prose facts and exact paths/numbers outside quotes still require recovery probes to detect.

Repair may add one paid call and is explicitly configurable; `noteRepair: false` restores one-pass size failure. Invalid notes, transport errors, cancellation, source changes and a second over-limit result do not trigger further repair. No truncation or checkpoint publication occurs on failure. The ordinary final source-snapshot and storage checks still apply after all calls. Per-call phase, elapsed time, returned usage and parsed JSON byte measurements survive failure; a call without returned usage has unknown cost, and an unparseable or cancelled response has no inferred byte measurement.

New checkpoints store an optional versioned `noteBudget` decision. Publication and reopening validate its shape and hard limit against the 8,000-token storage ceiling, not current generation preferences. A checkpoint without this metadata retains the legacy 6,000-token reading limit. This permits smaller generation settings or a model switch without invalidating existing evidence; final provider payload guards still enforce the selected model's capacity. Malformed budget metadata is rejected. The reviewed-copy migration script uses the same budget selection and stored-limit validation. Existing sessions are never rewritten. Older binaries cannot open notes above their 6,000-token limit; such sessions must remain on v0.2.3 or newer.

Pi already has a next-response preparation hook after complete tool batches. At an automatic threshold with zero keep budget, the controller validates all active tool pairs and lets the handover cover the finished batches, leaving the note for the next response. It does not retain an ever-growing unfinished user turn. This fixed in-task policy is hard compaction; the same host can also compact after a completed task turn. Manual compaction, overflow retries and explicit positive keep budgets retain the rules above. Adaptive selection between hard and soft compaction is future work. No new scheduling hook or host interface is added.

Both writer paths use `min(model.maxTokens, max(4096, noteTokens × 2))` for the capacity check and the requested output limit. Reserving the model's full maximum output could previously reject a prefix that fit the actual writer request. The automatic threshold is unchanged. The writer still checks the complete handover instruction and refuses a genuinely oversized request; arbitrarily large tool results or citation manifests are not guaranteed to fit.

### Continuation protections

An automatic handover between tool batches must preserve the unfinished turn independently of the writer's choice of facts. The controller selects all original user messages since the last completed assistant response, including steering and requests before earlier checkpoints in the same turn. For text-only requests, it appends their complete text and entry IDs in chronological order under `In-progress user requests`. The section identifies them as historical inputs, gives later user messages precedence and tells the model to continue from recorded progress rather than repeat completed work. The writer receives the same originals and must return a nonblank `nextSteps` item; final reporting is a valid next step. This is a structural requirement, not a semantic completion test.

Pinned requests count toward the post-compaction allowance and are measured separately as `continuationTokens`. If their complete text cannot fit, the handover fails without truncating it. If an active user request contains an image, the complete original turn remains in context instead of embedding an image placeholder in the note. This can prevent useful shrinking of a large multimodal turn; capacity failure remains explicit. Completed-turn, manual, overflow-retry and positive-keep-budget policies remain as described above.

The checkpoint adds an optional `continuation` array of original entry IDs. Publication and reopening recompute the unfinished requests from the source branch and check their IDs, exact rendered text and nonblank next step. Existing valid checkpoints without this field remain readable, but do not retroactively gain the new protection. Source-hash mismatches and summaries inconsistent with their validated note are now errors rather than an absent-memory result, including when memory is disabled.

The resident is appended after ordinary extensions. Its `context` handler requires exactly one `compactionSummary` matching the current committed summary, and its final payload guard requires that summary text to remain present after serialization. This closes the path where storage succeeds but another extension removes or substitutes the recovery note. Provider adapters that transform this text may be rejected and need compatibility verification. These guards check content at the local request boundary; they cannot prove remote processing, prevent a deliberately hostile extension from bypassing the host, or ensure the model follows a correctly restored note. No new host file, background writer or history database is added.

When the branch already holds earlier context-memory checkpoints, the host appends a `priorCheckpoints` section to the rendered note. Each item is the nearest readable original at or before the checkpoint's `coveredThrough` (a model or thinking change can be the leaf at compaction time and is not readable) and the opening sentence of up to three state items, whitespace-flattened and bounded by estimated tokens, so a Chinese sentence costs the same share as an English one. Items are oldest first within about 600 estimated tokens; over the bound, middle items are dropped first and the newest last, because the newest is the note the writer just merged and the oldest is the phase most likely to have been dropped. Checkpoint entry IDs are never rendered, since `context_history` cannot read them, and the section states that its IDs are anchors, not citable sources; a writer that cites one still fails `CONTEXT_NOTE_SCOPE`. The list is assembled from stored checkpoints, not written by the model. It is part of the rendered summary and counts toward the post-compaction size check, not toward the writer's note budget; when that check would fail, the list shrinks first and only then is the checkpoint refused. Compaction events record it as `lineageTokens`, separate from `noteTokens`.

`context_history` searches or reads the current ancestor chain. Search ranks by matched terms, then conversation turns (user, then assistant) above tool output, then newest first, so a single-word query no longer opens with the earliest and longest tool result on the branch. Results are ranked, not chronological; each excerpt carries its branch `position`, and the ranking version is part of the cursor signature so a cursor from an earlier build is rejected rather than resumed at a shifted index. Parent hosts can grant a particular child access to a frozen source range. Revocation stops further reads. Grants exclude later parent messages, sibling branches and recursively inherited authority. Cross-process manifests require parent identity and source checks.

## Persistence limits

The lease uses an atomic directory adjacent to the session. Stale ownership is reclaimed only when process identity establishes that the owner is gone. Unknown ownership requires inspection. Append failure attempts to restore the original length; failed rollback poisons storage and preserves a recovery marker.

External-write checks compare device, inode, length and mtime. Metadata-only ctime changes are not treated as content writes. This is a cooperative consistency guard, not protection against a hostile process that rewrites files and restores timestamps. Atomic publication and file fsync do not establish verified recovery from every power-loss or filesystem failure.

Disabled mode returns to Pi's default compactor after restart. Summaries remain readable and custom entries remain archived. Storage and opaque-history checks still apply. Windows persistence and network-filesystem locking are unsupported.
