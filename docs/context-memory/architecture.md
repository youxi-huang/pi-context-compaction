# Architecture

The original session JSONL is the history store. A checkpoint contains a structured note plus source identifiers and a branch snapshot. Original records remain available through a bounded history API.

## Runtime modules

| Module | Responsibility |
| --- | --- |
| `config.ts` | Process-latched enable flag, writer selection (`session` or a fixed `provider/model`), kept-context, note and compaction-point budgets. |
| `loader.ts`, `extension.ts`, `policy.ts` | Resident loading, tools, ownership, handler ordering and competing-compactor rejection. |
| `controller.ts` | Freeze source, choose the cut, invoke writer, validate candidate and block requests after failure. |
| `writer.ts`, `notes.ts` | Session writer over the current provider prefix, fixed writer over raw-source chunks, structured notes, quotation/citation checks and accumulated usage. |
| `history.ts`, `grant-file.ts` | Snapshots, bounded search/read, child identity and revocation. |
| `lease.ts`, `storage.ts` | Process identity, writer ownership, atomic first publication and append rollback. |
| `events.ts` | Local append-only evaluation log: outcomes, error classes, durations and counts, with per-session quotas and no content. |
| `identity.ts`, `build.ts`, `index.ts` | Format identity, source fingerprint and public integration surface. |

## Host changes

The SDK wraps resource loaders so ordinary filtering cannot remove the resident. Runtime construction checks ownership and tools. The extension runner propagates request-blocking failures from the resident instead of swallowing them. For `session_before_compact` it runs other extensions first and the resident last; a non-resident handler may observe the event and return `undefined`, but any returned compaction or cancellation is rejected before the writer runs.

`SessionManager` calls storage before publishing candidate entries to its in-memory tree. This includes first flush and subsequent writes. Session opening, branching and forking acquire a destination lease before exposing writable state. Extension events alone run too late to enforce these boundaries.

The controller returns a compaction candidate to Pi's existing commit path. It does not append checkpoints or replace agent messages itself. Storage checks the source snapshot again at commit. Cancellation, changed sources and disk failures leave the candidate uncommitted. Failed compaction blocks the next provider request until explicit retry or new input.

Each attempt the resident starts is settled exactly once in the event log: on `session_compact` as committed, or on `session_compact_failed` as failed or aborted with the error class recorded by the controller. A failure reported by Pi without a resident attempt is logged only when it carries one of the extension's own error classes, such as a competing compactor; host refusals like "nothing to compact" are not attempts. Every guard rejection is logged except repeated `CONTEXT_BLOCKED` within one failure, which is logged once. Logging never changes compaction behavior; a log write error is shown by `/compaction-status` and otherwise ignored.

Writer accounting is collected before note validation: `writerCalls` counts started calls and `usageReports` counts returned usage records, including an invalid note or cancellation after the response. Usage is accumulated once across fixed-writer chunks. Calls without a returned usage record have unknown cost. `writerMs` also survives writer failure. The report's existing `tokens` fields retain their committed-compaction meaning; `writerAttempts.all` and `writerAttempts.byOutcome` add known usage across all outcomes, unreported calls and legacy attempts without call counts. A malformed JSON note is `CONTEXT_NOTE_INVALID`, without copying its text into the error.

## Notes and retrieval

Two writers exist and neither substitutes for the other. The default `session` writer sends the session model its own next provider request, meaning the current system prompt, active tool definitions and converted messages in the same order Pi would send them, followed by one closing user message that carries the note schema, the rules, the previous note, increment candidates, bounded excerpts of referenced originals and a manifest mapping each uncovered entry to its ID with its opening words. The manifest exists because entry IDs are not visible inside the conversation; it shrinks to IDs only when the window is tight, and the request fails with `CONTEXT_WRITER_CAPACITY` rather than dropping the prefix. The prefix is rebuilt the way the resident's own `context` handler shapes it, including the pending-notes message, and drops a trailing failed assistant message the way overflow recovery does; other extensions' `context` handlers are not replayed, so an extension that rewrites the context on every request also defeats the provider's prompt cache. Prefix size is estimated with Pi's message estimator, so images count at their flat estimate rather than as base64 text. A fixed writer must exist in the catalog and its provider must have configured authentication; either failure is `CONTEXT_WRITER_UNAVAILABLE`. A fixed `provider/model` writer instead receives the previous note, new original records in sequential chunks and bounded excerpts of referenced originals. The session writer reasons at the session's current thinking level, mirroring Pi's own summarizer; `writerEffort` applies to a fixed writer only, and no effort is sent to a model without declared reasoning support. The effort actually sent is recorded in the compaction event as `writerEffort`. Increment notes are unverified candidates. Every quote must appear verbatim in a cited record; every source must be on the selected branch. These checks establish reference consistency, not semantic completeness.

The controller chooses the cut itself instead of adopting Pi's `keepRecentTokens` cut. With the default budget of zero, nothing is kept once the last turn is complete and the checkpoint's `firstKeptEntryId` is the sentinel `context-memory:keep-none`, which Pi's context assembly already treats as "no kept entries"; the next request holds the system prompt, the note and the new input. An unfinished turn, or an overflow retry, keeps from its own user message so tool calls and results stay paired. If no new user turn has started since the checkpoint, that message may be inside its kept prefix; repeated compaction follows the stored `firstKeptEntryId` to find it. Once a new user turn exists, a positive budget stays after the previous checkpoint, as before. A session smaller than the budget keeps its latest turn. Context assembly omits older compaction entries that lie inside a retained turn, leaving one current summary plus complete tool rounds. Those checkpoints and original records remain on disk, and `priorCheckpoints` remains in the current summary. Storage accepts the sentinel; every other `firstKeptEntryId` must exist on the branch. Pi's `findCutPoint` also falls back to the latest cut point instead of the first when the budget is met inside the trailing entries of the last turn, so a branch ending in a tool result still prepares a compaction.

The compaction threshold is `min(model cap, 0.8 × context window, context window − output reserve, compactAt)`. Caps are 400,000 for GPT and 200,000 for Gemini; other families have no extra cap. The final input allowance is separately `context window − output reserve`, including the serialized-payload check. The threshold is a preferred trigger, not the input allowance: using it for both could reject a request before the host's different token estimate reached the trigger. Estimates are conservative approximations, not billing measurements.

Pi already has a next-response preparation hook after complete tool batches. At an automatic threshold with zero keep budget, the controller validates all active tool pairs and lets the handover cover the finished batches, leaving the note for the next response. It does not retain an ever-growing unfinished user turn. This fixed in-task policy is hard compaction; the same host can also compact after a completed task turn. Manual compaction, overflow retries and explicit positive keep budgets retain the rules above. Adaptive selection between hard and soft compaction is future work. No new scheduling hook or host interface is added.

Both writer paths use `min(model.maxTokens, max(4096, noteTokens × 2))` for the capacity check and the requested output limit. Reserving the model's full maximum output could previously reject a prefix that fit the actual writer request. The automatic threshold is unchanged. The writer still checks the complete handover instruction and refuses a genuinely oversized request; arbitrarily large tool results or citation manifests are not guaranteed to fit.

When the branch already holds earlier context-memory checkpoints, the host appends a `priorCheckpoints` section to the rendered note. Each item is the nearest readable original at or before the checkpoint's `coveredThrough` (a model or thinking change can be the leaf at compaction time and is not readable) and the opening sentence of up to three state items, whitespace-flattened and bounded by estimated tokens, so a Chinese sentence costs the same share as an English one. Items are oldest first within about 600 estimated tokens; over the bound, middle items are dropped first and the newest last, because the newest is the note the writer just merged and the oldest is the phase most likely to have been dropped. Checkpoint entry IDs are never rendered, since `context_history` cannot read them, and the section states that its IDs are anchors, not citable sources; a writer that cites one still fails `CONTEXT_NOTE_SCOPE`. The list is assembled from stored checkpoints, not written by the model. It is part of the rendered summary and counts toward the post-compaction size check, not toward the writer's note budget; when that check would fail, the list shrinks first and only then is the checkpoint refused. Compaction events record it as `lineageTokens`, separate from `noteTokens`.

`context_history` searches or reads the current ancestor chain. Search ranks by matched terms, then conversation turns (user, then assistant) above tool output, then newest first, so a single-word query no longer opens with the earliest and longest tool result on the branch. Results are ranked, not chronological; each excerpt carries its branch `position`, and the ranking version is part of the cursor signature so a cursor from an earlier build is rejected rather than resumed at a shifted index. Parent hosts can grant a particular child access to a frozen source range. Revocation stops further reads. Grants exclude later parent messages, sibling branches and recursively inherited authority. Cross-process manifests require parent identity and source checks.

## Persistence limits

The lease uses an atomic directory adjacent to the session. Stale ownership is reclaimed only when process identity establishes that the owner is gone. Unknown ownership requires inspection. Append failure attempts to restore the original length; failed rollback poisons storage and preserves a recovery marker.

External-write checks compare device, inode, length and mtime. Metadata-only ctime changes are not treated as content writes. This is a cooperative consistency guard, not protection against a hostile process that rewrites files and restores timestamps. Atomic publication and file fsync do not establish verified recovery from every power-loss or filesystem failure.

Disabled mode returns to Pi's default compactor after restart. Summaries remain readable and custom entries remain archived. Storage and opaque-history checks still apply. Windows persistence and network-filesystem locking are unsupported.
