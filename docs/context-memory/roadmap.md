# Roadmap

This document states where the project is going and how each step will be judged. It is a statement of intent, not a schedule. Release dates are not promised, and the order of the middle steps may change once daily use shows which problems matter most.

## Version policy

Patch releases (0.x.y) carry adaptation and corrections to already promised behavior: ports to new Pi releases, interface changes, dependency and security updates, CI fixes, and defects in compaction, persistence or accounting. New compaction strategies and capabilities normally belong in minor releases. v0.2.3 is an explicitly maintainer-approved exception: it brings forward tiered note allowances and one bounded same-writer size repair, alongside budget compatibility and accounting fixes. v0.3.1 is a second explicitly maintainer-approved exception, delivering the first bounded stock-Pi extension preview as a patch-version increment. v0.3.3 is mainly a set of corrections, and the maintainer also selected a patch release for the read-only `/compaction-doctor` command and the added status fields that ship with them. These are documented behavior additions, not relabeled as bug fixes.

Minor releases (0.x.0) each answer one question about the project. A minor release ships when its acceptance criterion is met, not when a date arrives.

An independently installable stock-Pi extension is a committed pre-1.0 delivery goal. Its first public release may be a 0.x preview with a clearly stated supported scope. Version 1.0 marks a mature independent extension with a stable compatibility and recovery contract; it is not permission to distribute the extension for the first time. Implementation uncertainties determine the work and release timing, not whether this goal belongs on the roadmap.

## Goals and how they are measured

The long-term aim is compaction that is small, precise and unobtrusive: little token overhead, notes that let the next model continue the task without asking again, and no visible pause or interruption when things work. Unobtrusive does not mean silent on failure. The project deliberately reports a failed compaction and stops requests rather than substituting a different writer or a weaker summary, because a note whose sources cannot be trusted is worse than no note. That choice stays.

Four measurements track the goals:

- Compaction pause: wall-clock time from the compaction trigger to the next provider request.
- Recovery accuracy: correct recovery of facts, supporting evidence, current authority and the next task step, using replayable synthetic sessions. Report the components separately under the evaluation contract below.
- Token overhead: writer tokens and note size relative to the original records they replace, with retrieval usage reported separately. Include known usage from failed, cancelled and discarded work; identify calls with missing usage reports.
- Host footprint: for each host, how the method attaches (extension points of an unmodified host, or a modified host) and the lines changed against that host, which is zero for an unmodified host.

## Architectural direction

The durable facts of a session are the original records and the committed checkpoints that reference them; both stay on disk and are never rewritten. Everything built on top — rendered summaries, retrieval indexes and other sidecar artifacts — is a derived projection that can be deleted and rebuilt from those records. The planned work moves compaction from one synchronous rewrite at the boundary toward increments prepared while the task runs, with the boundary doing validation and assembly and the full commit gate retained. This direction draws on public community work on agent context management, including incremental and rolling compaction, reversible context reduction and provider-native compaction state. The source-linked checkpoint remains the authoritative recovery path.

**Host-neutral core.** The method is not specific to Pi. Its guarantees are stated in terms of records, branches, checkpoints and a commit gate, and a host supplies the extension points that enforce them. From 0.7.0 the project separates a host-neutral core from host adapters. The core owns the note and checkpoint formats, validation, repair, retrieval views, background preparation, call accounting and the failure states. An adapter owns lifecycle events, model transport, tool registration and the place where checkpoints are stored. Pi is the reference host: core changes are verified on Pi first, and the Pi extension keeps every promise its releases have made. dsh (DeepSeek's official agent), Codex, OpenCode, Claude Code and other hosts are compatibility targets, not the definition of the project. These rules hold for every adapter:

- Original records stay in the host's own storage. The core keeps no copy of history, and its derived views are computed on demand or disposable.
- Citations use the host's own record IDs. The core never invents a record ID, and a checkpoint identifies the host and adapter that wrote it; Pi checkpoints without that field are read as Pi's.
- Each adapter declares how it attaches, through extension points of an unmodified host or as a modified host, and the guarantee level its host allows. Status output and documentation report both. A modified host is labelled and evaluated apart from unmodified ones, as the resident build is today.
- No adapter falls back silently. An adapter that cannot stop requests after a failed compaction says so, rather than presenting the host's own fallback as protected.
- The writer contract (schema, rules, quotable text, repair and accounting) is shared. The transport belongs to the adapter, because prompt-cache reuse depends on reproducing the host's own request, as the 0.5.0 cache fix showed.
- Background preparation belongs to the core. It does not rely on a host's own asynchronous compaction, which a host may switch off when an extension takes part in compaction.

| Guarantee level | The host lets the adapter | What holds |
| --- | --- | --- |
| Gated | Supply the compaction result, stop requests after a failed or unconfirmed checkpoint, read the committed checkpoint back and offer retrieval | Every guarantee, including failure blocking |
| Checked | Put a validated note into the model's context and offer retrieval, without stopping requests or the host's own compaction | Commit checks and retrieval; failures are reported, not enforced |
| Traceable | Read records and offer retrieval or offline verification | Retrieval within the branch and verification of stored checkpoints |

## Planned minor releases

**Source-hash follow-up, unassigned.** `hashEntries` hashes `JSON.stringify()`
output, so reordering object fields without changing their values can reject a
checkpoint. v0.5.0 keeps the existing algorithm and stored format. A future
canonical serialization needs an explicit compatibility plan for existing
checkpoints and regressions that distinguish harmless field reordering from
changed source content; citation checks alone cannot replace the latter check.

**0.2.0, daily use.** Released 2026-09-09. The maintainer's own Pi installation runs this build as its only compactor, and the local event log records every compaction attempt. The deliverable of the 0.2.x period is a list of what feels slow, wrong or noisy in ordinary work; the first real two-checkpoint session already produced three changes that shipped in 0.2.0 itself. Every later release is shaped by that list.

**0.3.0, measurement — released 2026-10-09; evaluation implemented, minimal live validation executed, full baseline deferred.** The release contains replayable synthetic fixtures, probes, deterministic scoring, a Pi runner and an explicitly authorized subscription runner under [the evaluation contract](../../eval/README.md). It answers the measurement question at the level of method: recovery can be measured reproducibly, and the first live record is partial. Each evaluated runtime is pinned and reported with its results. The intended native-Pi comparison is not complete: under the reduced evaluation budget, the remaining 16 runs were closed as unstarted rather than replaced by a claimed baseline.

The bounded Luna/max exercise retained failures and partial native results. An initial project-only check was rejected by its 10,000-token output limit. The final authorized calibration raised the writer's total output allowance to 32,768 including reasoning, kept the 600-second writer deadline and original note commit limits, and allowed only the seven requests remaining from the eight-request envelope with one reset of the ten-minute window. The first checkpoint and its state/action/permission continuation passed; the second writer completed but the note cited an exact quotation to the wrong source entries, so commit was refused. Four final requests were used in about 556 seconds. This is a completed measurement attempt with partial success, not acceptance of continuous two-checkpoint recovery; the [validation record](validation.md#03-measurement-bounded-live-validation-2026-09-22-utc) states the coverage and remaining limits. No further live attempt is scheduled. The v0.3.0 release ships this method and record together with the Pi v1.1.0 host port; it does not claim continuous two-checkpoint recovery or a completed native-Pi comparison.

Further live work should use one representative long chain and a small number of task-continuation checks with a declared request/time budget. Avoid repeated full offline matrices during routine iteration, keep only necessary evidence and remove regenerable scratch copies. A complete two-arm provider baseline remains deferred until sufficient budget is available. Cross-host and comprehensive multi-provider evaluation remain outside this scope. Extension migration is tracked separately, with each evaluated build and behavior change identified so later comparisons remain interpretable.

**0.3.1, independent extension preview.** Deliver the first public Git package for unmodified official Pi 1.1.0. The package-only branch supports installation and extension-only updates; immutable package tags support pinned installs. The bounded workflow is manual compaction of fresh persistent text turns, source-linked notes, current-branch original-history retrieval and continuation after reopening. Pending/blocked attempts persist, and explicit retry or recovery must confirm a validated checkpoint on disk before requests resume. Stock-Pi protocol and package-lifecycle acceptance uses synthetic loopback services; real-provider quality and broader workflows remain follow-up work. See the [preview scope](extension-preview.md) and [validation](validation.md#independent-stock-pi-candidate-2026-10-11-utc). The maintainer explicitly selected a patch-version increment for this delivery; v0.3.1 is an exception to the normal minor-release rule for new capabilities. The subsequent numbered milestones keep their original scope.

**0.3.2, ordinary retries.** Released 2026-10-11. Pi's ordinary retries after transient provider failures no longer block preview sessions, and sessions blocked by the earlier retry handling, or by a text-only context overflow, can recover through an explicit `/compact` once enough completed history exists. A default-settings scenario runner now records each preview behavior beside a stock-Pi control, with 17 checks kept as known gaps.

**0.3.3, existing sessions.** Installing the preview should not cost an existing session its usability. Sessions the preview has never protected and cannot check (another Pi version, in-memory sessions, native or foreign checkpoints, images) are left to Pi instead of being blocked, while sessions it protects keep every check. Failures and blocked inputs produce one actionable notice each, `/compaction-doctor` adds a read-only first-use check, and stock-Pi acceptance no longer risks linking against the repository's own build. Fifteen of the 17 known gaps become required checks. The remaining two measure long-session request overhead, about 1.1 seconds per request at 20 checkpoints in the synthetic scenario; reducing it without weakening disk readback or source validation is the next measured target.

**Instruction authority, a dedicated minor release, number assigned later.** A verbatim quotation proves that a source said something, not that the source may issue instructions. This release adds a mechanical distinction between sources that can produce instruction-level content and sources that can only produce evidence, informed by the instruction-authority failures that 0.3 measures. The contract must consider more than the message role: quoted or analyzed text inside a user message is not a user instruction, project rules have scope and can be revoked, and behavioral requirements can appear in any recovered section, not only under explicit instructions. Trusted-source labels are established by the host or a deterministic path, never claimed by the candidate note itself. The promise is bounded: prevent specified source classes from being mechanically promoted to instructions and test known confusion patterns; model adherence and semantic completeness remain outside it, as elsewhere. The original plan placed this gate before session-model increments. D18 later selects data-only work notes with verbatim user-message retention for the bounded B experiment; it does not deliver this broader authority protocol. A first step needs no new protocol: the rendered note shows, for each fact, the role of the records it cites (user message, tool output or assistant text), computed by the host from those records rather than claimed by the note. Stored checkpoints keep their existing rendering.

**0.4.0-preview.1, earlier A candidate, never published.** The maintainer initially selected an A-only experimental candidate with a version-bound performance exception. Later decisions D15–D18 replaced its validation, preparation and B design. Its [historical record](archive/v0.4.0-preview.1-release.md) remains separate from v0.4.0, and its exception cannot authorize another version.

**0.4.0, experimental latency paths.** The maintainer selects publication of the implementation merged in PRs #40 and #41, with strict synthetic acceptance. Completed-turn threshold compaction uses the manual commit gate. Arm A prepares with the configured writer; arm B merges data-only session-model work notes. Both are off by default. Validated prefix commits keep later originals verbatim, and B carries every covered user message in full or falls back to the configured writer. Every writer call is journaled. Preparation failures remain non-blocking; a failed compaction retains durable blocking and explicit disk-confirmed recovery.

The full strict stock-Pi scenarios, including the 50 ms request-overhead target and checkpoint-growth bound, remain required without exceptions or known gaps. Sources are checked in full at trust boundaries; a same-length rewrite between boundaries is found at the next boundary and cannot pass a checkpoint commit. Synthetic A/B controls and the finite Haiku bridge run establish execution mechanics and retain their failures. They do not establish real-provider whole-task latency, complete billing, cache behavior or semantic recovery benefits. Those original A/B acceptance goals remain follow-up work, rather than claims made by this experimental release. See the [release scope](v0.4.0-release.md).

**0.4.1, review fixes.** An independent review of v0.4.0 found that a writer note could open a Markdown heading of its own in a checkpoint and that arm B never closed a resolved open question; confirming it found that a B correction could drop facts it did not replace. v0.4.1 folds every committed writer fact onto one line in the preview and, with the maintainer's approval of a new fingerprint and evaluation pin, in the resident runtime. B replaces open questions when a note lists them and leaves an ambiguous correction to the writer. Optional `supersedes` and the growth of accumulated facts toward the schema's bounds remain, and wait for stable fact identities in the note schema.

Scheduling needs a separate evaluation in a later 0.x release. **Hard compaction** pauses an unfinished task at a safe boundary, writes and commits a handover, then resumes the task. **Soft compaction** waits until the current task turn is complete before compacting. Automatic selection and adaptation between the two are future work; a threshold change alone must not be presented as support for in-task handover. Hard-compaction acceptance requires actual automatic checkpoints and successful continuation across at least two boundaries, preserving early constraints and distinguishing superseded decisions. Neither mode permits incomplete tool-call/result pairs or an uncommitted handover to reach the next request.

**0.5.0, note quality.** Delivered in the independent preview only; the resident runtime, its build fingerprint and the evaluation pin stay as they are. Note structure is revised from evaluation failures rather than from intuition, and history retrieval gains a typed view so a model pages less. The view lists what committed checkpoints already record by section (constraints, decisions, failed approaches, files, plans), with superseded items marked, plus edits and errors read from tool records. It is derived from the records and checkpoints on every call, so it never goes stale; it is persisted only if measurement shows the need. Its results are original excerpts from the current branch, so a hit never widens branch or grant access. The view says it can miss what a writer left out, and search remains. Accepted when recovery accuracy rises and average retrieval calls fall, with per-call build cost and missed-entry probes reported; fewer calls with lower accuracy is a failure, not a saving.

Writer quotation accuracy belongs to the same release and ships with it. In both bounded live runs a writer cited an exact quotation to entries that do not contain it, and `CONTEXT_NOTE_QUOTE` refused the commit: the second writer of the [0.3 measurement](validation.md#03-measurement-bounded-live-validation-2026-09-22-utc) and the first writer of the [v0.4.3 DeepSeek run](validation.md#v043-bounded-provider-run-on-official-pi-130-with-deepseek-v41-flash-2026-10-16-utc). The guard stays; the work is to make the failure rarer and cheaper. The session writer will see each user message's full text beside its entry ID. The single same-writer repair, which today covers only note size, will also cover quotation, with at most one repair of either kind per compaction. A quotation repair names each failing quotation, the entries it cites and the entries that do contain it, with their roles, and asks for replacements of those facts only. The host never rebinds a quotation itself. A repaired note passes the same commit checks, and a second failure blocks as it does now; there is no other writer and no unchecked summary. Accepted when quotation refusals fall across recorded runs without lower recovery accuracy, with repair calls and pause time reported. The [v0.5.0 plan](v0.5.0-plan.md) records the decisions, work packages and gates. v0.5.0 met them in its second DeepSeek run; on the way the session writer stopped sending `tool_choice: "none"`, which had kept it from DeepSeek's prompt cache, and now declines one tool call per compaction instead.

**0.6.0, footprint.** v0.2.3 brings forward source-size tiers, limited budget elasticity and serialized-note measurement to address daily failures. This milestone remains the evidence-based refinement of those initial parameters and writer overhead, not a second introduction of the same features. It also evaluates reversible reduction: removing already consumed or superseded tool results from the writer input and the active context as a view-level change while the originals stay in the session records. Stored originals alone do not make removal safe; eligibility rules must keep active requests, complete tool pairing and sole evidence for later decisions, and the cost of paging removed content back in counts against the saving. The first candidates need no model call, following the deterministic tiers of Better Compact: an earlier read of a file that was read again later, and a consumed tool result, each replaced by one line that names the tool, its target, the first line of its result and the record ID, which `context_history` reads back in full. Nothing in the session file is rewritten, unlike hosts that shrink stored entries in place. Following Oh My Pi, a reduction touches an entry only when few tokens follow it, so the cached suffix it invalidates is short, or waits until the session has been idle longer than the cache lifetime; it should not cost more cache writes than it saves. The rendered note is measured the same way. Candidates are current state, standing instructions and next steps in full, with older failed paths and reasons as one line each with their source IDs, and no rendered text that changes with the time of rendering. For retrieval, the candidates are to state what a full read would cost before making it, to return low detail first and to mark results already in context; the 0.5.0 typed view covers part of this. A further candidate, after LCM, appends a short original excerpt when the user's prompt names an exact identifier that is no longer in context. The excerpt is labelled as historical evidence with its record ID and role, placed at the end of the context so the cached prefix is untouched, filtered for secrets, and counted as retrieval; excerpts the model did not need are reported. Accepted when token overhead falls while recovery accuracy holds.

**Unobtrusive compaction, a dedicated minor release, number assigned later.** The pause is still one synchronous writer call. In the v0.5.0 bench the median pause was 12 to 14 s with 96 to 97% of the writer's input read from cache: the time goes to writing the note, not to reading history. Synthetic runs of arm A already showed that preparation removes that call from the pause when it finishes in time, about 1.1 s down to about 0.1 s at a simulated second of latency. This release makes the boundary an assembly step. While the task runs, the core prepares source-linked segments for closed ranges of completed turns and validates each one as it returns, with the same source and quotation checks as a commit. At the boundary the previous checkpoint and the validated segments are merged without a model call, the source snapshot and disk readback are checked, and every original after the last segment stays verbatim, as the prefix path does today. When the segments do not cover enough, the synchronous writer runs as now, and its failure still blocks. Segments are derived from the records and stay in memory; persisting them is a scope decision taken only if measurement shows that losing them on restart costs too much, and they never become a second history store. Earlier segments render unchanged, so a provider can reuse the cached prefix across checkpoints. Candidate triggers are a segment length of completed turns, a bounded band in which a request may wait for a preparation in flight without passing the context guard, and a commit after the user has been idle longer than the provider's cache lifetime, when the cache is cold anyway. Arm B's data-only work notes become an optional hint rather than the main path. Cheap boundaries also make the hard compaction described above affordable. Two decisions come first. Stable fact identities, deferred in 0.5.0, let a segment replace a fact instead of accumulating it. And when accumulated segments outgrow the note budget, whether they may be merged by the writer under the full commit checks, keeping every source and quotation as the size repair does, is decided against the 0.5.0 rule that excludes unchecked rewriting in the style of Mastra's reflector. Background preparation keeps repair off unless the maintainer decides otherwise. It also keeps hard limits, extended from today's deadline and call count: a cap on calls and spending per interval, and a breaker that pauses preparation after consecutive failures. Either limit sends the next compaction to the synchronous path rather than blocking work, and every call stays in the journal. Regressions include a seeded coverage test in the manner of Mastra's: scripted segments embed the record IDs they cover, and across restarts, branch changes and failed preparations every original must be covered by a validated segment or kept verbatim, never neither. Accepted on provider runs when pause P95 falls and recovery accuracy holds, with validated coverage at the trigger, discarded and failed preparation cost and total writer tokens reported beside the synchronous control. The design follows LCM's hidden summaries published without a model call, Mastra's buffered observations activated at a threshold and Oh My Pi's preparation and grace bands. None of them checks what its summaries say, and this release keeps that check.

**0.7.0 to 0.9.0, a host-neutral method.** These three releases turn the Pi extension into the first adapter of a [host-neutral core](#architectural-direction). Each answers one question. Their order may change when a capability review or daily use shows a better one, but every release keeps the guarantees already promised on Pi, and a scope change is documented with its consequences.

**0.7.0, a host-neutral core.** Can the method be stated and run without Pi? The release writes the specification and moves the preview's host-independent logic into a core package that imports nothing from Pi; `verify` rejects any host import into it. The Pi extension becomes the core's first adapter, with no change in behavior. The specification defines the record model, the note and checkpoint formats, validation, the commit and failure states, retrieval and call accounting, and names the check that enforces each guarantee. It defines a source hash by its properties: deterministic for the same records, and changed when cited content changes under the same ID. The Pi adapter keeps `hashEntries`, so every stored checkpoint reads as before; a canonical serialization for later hosts follows the compatibility plan of the source-hash follow-up above. The preview fixtures gain a host-neutral record format with a converter to Pi sessions, and validation gains conformance vectors: records and candidate notes that every implementation must accept, or refuse with the same error class. The resident runtime stays as it is. The core starts from copies of the shared files, so the resident fingerprint and the evaluation pin do not move. Accepted when the core builds and tests without Pi packages; the Pi extension passes strict stock-Pi acceptance and the scenarios on every listed Pi version, with the same notes, citations and error classes for the same scripted inputs; v0.4.x and v0.5.x checkpoints reopen; and the P1 to P3 offline results reproduce.

**0.8.0, a second host.** Does the core hold on a host it was not built for? The release starts with a capability review, as the Pi preview did: for each candidate host it maps the public extension points to the adapter's duties and to a guarantee level, and it chooses one host whose structure differs from Pi's. Codex, through its hooks, is the current lead; the review makes the choice. A host that attaches the way Pi does, such as dsh, does not answer this question: its adapter starts from the Pi adapter and may follow as soon as 0.7.0 provides the core. The adapter ships at the level its host allows and says so in its status output and documentation. A change the core needs is made host-neutral and verified on Pi first; the core carries no branch for a particular host. Acceptance runs on isolated official installations of the second host, as stock-Pi acceptance does, and the host-neutral fixtures produce a recovery report for each host, never pooled. Accepted when the second adapter passes the conformance vectors and its own acceptance, the Pi extension passes unchanged, and every report states the host's guarantee level next to its results.

**0.9.0, a contract to support.** Is the contract stable enough to promise across hosts? Further adapters, such as dsh, OpenCode or Claude Code, follow the same review and are added as demand and their extension points allow. Where only a modified host can carry the method, as currently expected for Claude Code, the adapter is labelled and evaluated as one. The specification reaches a 1.0 candidate: frozen note, checkpoint and citation formats, a compatibility and migration policy across core versions and adapters, versioned core and adapter interfaces, and deprecation rules. The validator is published as a package of its own with the conformance vectors. It may also check another compactor's summaries wherever they cite records in the host's own format; such a check reports reference consistency only, and is offered as an option, not as a claim about that compactor. Each host's native compaction becomes that host's external baseline on the same fixtures. The maintainer decides the project's name, repository layout and distribution channels in this release; stored identifiers keep their current names. Accepted when Pi and at least one other host pass conformance and acceptance on the release candidate, checkpoints written by earlier versions open as the policy states, and the cross-host report publishes accuracy, pause and token cost per host, including results that favor a baseline.

**1.0.0, mature and host-neutral.** A stable specification and core interface, with the conformance vectors published. The Pi extension meets the bar set before: a stable supported Pi range, a verified configuration and checkpoint compatibility and migration policy, repeatable recovery and failure-handling evidence, and a maintained install, update and remove path on unmodified Pi. At least one further host runs at its declared guarantee level with acceptance evidence. The support matrix is defined from evidence; neither every host nor every host version is required. First installability alone does not establish maturity, and users do not have to wait for 1.0 to use any adapter.

The [v0.4.0 latency implementation plan](v0.4.0-plan.md) breaks the latency milestone into work packages, candidate and commit contracts, accounting, integration decisions and release gates. It records the implementation decisions and their earlier candidates; the release document states the current delivered scope and outstanding provider measurements. Companion [instruction-authority](archive/instruction-authority-design.md) and [historical-prefix](archive/historical-prefix-design.md) proposals preserve the earlier trust, temporal projection and compatibility designs; D16–D18 define the delivered prefix and data-only B paths. Conditional retained-tail reuse and any change to the two-arm comparison require explicit scope decisions rather than silently changing this roadmap.

## Evaluation contract

Recovery reports separate fact and exact-value accuracy, source support, superseded-decision handling, instruction authority and task continuation. A valid source ID or verbatim quotation does not establish that the source supports the claim or remains the current ruling. Include unapproved proposals and internal writer instructions so they cannot be mistaken for user authorization. Continuation checks cover the next task action, early constraints, repeated work and premature completion, alongside question answering.

Include questions whose answers are absent from the records. Report correct, incorrect and omitted or abstained answers, plus unsupported historical claims, with explicit counts and denominators. Distinguish unsupported claims from claims based on real but superseded or misinterpreted evidence. Report compaction failures and blocked continuations across all attempts, alongside recovery scores for completed probes; do not discard failed attempts or treat abstention alone as success.

Probe independent checkpoint copies so earlier probe answers do not leak into later ones. Pin and report fixture/scorer versions, host and compactor revisions, models, reasoning settings, budgets and tool access. Publish repeat counts and variation, not only the best run. Replayability means the inputs, procedure and scoring can be inspected and rerun; it does not promise identical model responses.

Ordinary CI checks fixture integrity, source mappings, scoring, report generation and deterministic regressions without provider calls. Explicitly triggered provider evaluations measure semantic recovery and live costs under a stated run budget. Scripted responses and replayed outputs are not new provider-quality measurements. Keep fixtures and scoring independent of any host's runner so the method can evaluate other handover mechanisms. From 0.7.0 fixtures use a host-neutral record format, which each host's runner converts into that host's sessions.

## External baseline

The first recovery comparison is against Pi's native compaction on the same pinned Pi baseline, task model and replayable probe set. Reports must state compaction settings, retained-context budgets and allowed retrieval tools so the comparison can be interpreted. Provider-native compaction, where available, is an additional external baseline and is reported separately.

Once the native Pi comparison is stable, a same-host third-party compactor may be added. [Better Compact](https://github.com/AshishKumar4/better-compact) is a candidate, subject to compatible versions and the cost of a fair comparison; it does not block 0.3. Allow each compactor its documented recovery mechanism, report active-context size and retrieval cost, and accept verifiable source locations rather than requiring this project's entry-ID format. State budget differences instead of presenting unequal retained context as an equivalent comparison.

From 0.8.0 each supported host's native compaction is that host's baseline on the same host-neutral fixtures. Results are reported per host with its guarantee level. A comparison across hosts states their differences in retained context, retrieval tools and enforcement instead of ranking them as equivalent.

Whether source-linked compaction recovers tasks well enough to justify its pause, token and retrieval costs is still an open question. Reports will publish the trade-offs, including results that favor a baseline. Those results determine which parts of the project remain worth maintaining.

## Public extension delivery and acceptance

This section is the Pi adapter's commitment. From 0.7.0 the extension is built on the host-neutral core and keeps every promise below.

**Committed goal:** an independently installable, configurable and updatable extension on unmodified Pi, released for public use before 1.0. Pi remains maintained and updated upstream. This project maintains the extension, its dependencies and its declared compatibility. **Current status:** the released resident implementation still requires host changes. The separate [stock-Pi preview](extension-preview.md), currently v0.5.0, supplies the bounded workflow through an extension-only Git package, an isolated acceptance runner and default-settings scenarios, and leaves sessions it never protected to Pi. Real-provider trial, broader compatibility and 1.0 maturity remain outstanding; request overhead is checked under the strict synthetic profile. The existing source build supports development and comparison during migration, not a separate binary distribution product to expand.

Use Pi's Git/npm package facilities for installation and updates. A GitHub-hosted package is a valid initial channel; npm is optional. Document supported Pi versions, first-run setup, extension-only updates and how to select a newer pinned release. Preserve credentials, settings, sessions and other extension registrations. Do not replace the Pi executable, patch installed host files or rely on private host internals and call that independence.

The first public 0.x package must provide a useful end-to-end workflow: install on stock Pi, configure, compact into a source-linked note, retrieve supporting originals, resume the supported task/session, and update the extension independently. Verify source checks and failure behavior, plus disabling/removing the extension and compatible rollback. State which host versions, providers, session formats and workflows were tested. A preview can start with a bounded support matrix and documented limitations; it does not need every maturity criterion or optimization planned for 1.0.

Define the preview's supported scope and differences from the resident build before release. Core source integrity, user authority and explicit compaction-failure handling remain requirements within that scope. Broader resident-build guarantees, such as persistence across deliberate extension disabling or additional concurrency scenarios, must be assessed individually rather than silently promised or automatically imposed as preview gates. Describe unsupported workflows and their practical consequences. Existing custom sessions must either have a verified transition path or remain on their compatible implementation while the preview uses fresh sessions; installation never silently migrates original data.

The host-dependency review is the first implementation step, not the final deliverable. Where an upstream gap or a scope decision blocks progress, report the specific dependency, affected guarantee and proposed resolution. Adjust implementation, support scope or release timing explicitly; do not replace the public-extension goal with an open-ended investigation. Record preview evidence separately from resident-build results. Search rank and a separate Pi updater are outside this objective; additional hosts belong to the 0.7.0 to 0.9.0 releases.

## After 1.0

Once the core and the Pi extension reach 1.0 maturity, their default state is maintenance: patch releases for adaptation and a periodic run of the evaluation against each host's native compaction. A new host is adapter work against the stable core and does not by itself require a new core release. Two directions would justify further minor releases. One is a provider-native compaction payload as an optional acceleration layer, bound to model and tool-catalog fingerprints, falling back to the source-linked checkpoint on any mismatch and never replacing it as the authoritative recovery path. The other is a broader memory scope, which is explicitly outside the current design; adding it would change what the project is, and it would belong in a separate project or a second major release, decided at that time rather than assumed now.
