# Roadmap

This document states where the project is going and how each step will be judged. It is a statement of intent, not a schedule. Release dates are not promised, and the order of the middle steps may change once daily use shows which problems matter most.

## Version policy

Patch releases (0.x.y) carry adaptation and corrections to already promised behavior: ports to new Pi releases, interface changes, dependency and security updates, CI fixes, and defects in compaction, persistence or accounting. New compaction strategies and capabilities normally belong in minor releases. v0.2.3 is an explicitly maintainer-approved exception: it brings forward tiered note allowances and one bounded same-writer size repair, alongside budget compatibility and accounting fixes. These are documented behavior additions, not relabeled as bug fixes.

Minor releases (0.x.0) each answer one question about the project. A minor release ships when its acceptance criterion is met, not when a date arrives.

An independently installable stock-Pi extension is a committed pre-1.0 delivery goal. Its first public release may be a 0.x preview with a clearly stated supported scope. Version 1.0 marks a mature independent extension with a stable compatibility and recovery contract; it is not permission to distribute the extension for the first time. Implementation uncertainties determine the work and release timing, not whether this goal belongs on the roadmap.

## Goals and how they are measured

The long-term aim is compaction that is small, precise and unobtrusive: little token overhead, notes that let the next model continue the task without asking again, and no visible pause or interruption when things work. Unobtrusive does not mean silent on failure. The project deliberately reports a failed compaction and stops requests rather than substituting a different writer or a weaker summary, because a note whose sources cannot be trusted is worse than no note. That choice stays.

Four measurements track the goals:

- Compaction pause: wall-clock time from the compaction trigger to the next provider request.
- Recovery accuracy: correct recovery of facts, supporting evidence, current authority and the next task step, using replayable synthetic sessions. Report the components separately under the evaluation contract below.
- Token overhead: writer tokens and note size relative to the original records they replace, with retrieval usage reported separately. Include known usage from failed, cancelled and discarded work; identify calls with missing usage reports.
- Host footprint: lines changed against upstream Pi.

## Architectural direction

The durable facts of a session are the original records and the committed checkpoints that reference them; both stay on disk and are never rewritten. Everything built on top — rendered summaries, retrieval indexes and other sidecar artifacts — is a derived projection that can be deleted and rebuilt from those records. The planned work moves compaction from one synchronous rewrite at the boundary toward increments prepared while the task runs, with the boundary doing validation and assembly and the full commit gate retained. This direction draws on public community work on agent context management, including incremental and rolling compaction, reversible context reduction and provider-native compaction state. The source-linked checkpoint remains the authoritative recovery path.

## Planned minor releases

**0.2.0, daily use.** Released 2026-09-09. The maintainer's own Pi installation runs this build as its only compactor, and the local event log records every compaction attempt. The deliverable of the 0.2.x period is a list of what feels slow, wrong or noisy in ordinary work; the first real two-checkpoint session already produced three changes that shipped in 0.2.0 itself. Every later release is shaped by that list.

**0.3.0, measurement — evaluation implemented; minimal live validation executed; full baseline deferred.** The repository now contains replayable synthetic fixtures, probes, deterministic scoring, a Pi runner and an explicitly authorized subscription runner under [the evaluation contract](../../eval/README.md). Runtime compaction behavior remains pinned. The intended native-Pi comparison is not complete: under the reduced evaluation budget, the remaining 16 runs were closed as unstarted rather than replaced by a claimed baseline.

The bounded Luna/max exercise retained failures and partial native results. An initial project-only check was rejected by its 10,000-token output limit. The final authorized calibration raised the writer's total output allowance to 32,768 including reasoning, kept the 600-second writer deadline and original note commit limits, and allowed only the seven requests remaining from the eight-request envelope with one reset of the ten-minute window. The first checkpoint and its state/action/permission continuation passed; the second writer completed but the note cited an exact quotation to the wrong source entries, so commit was refused. Four final requests were used in about 556 seconds. This is a completed measurement attempt with partial success, not acceptance of continuous two-checkpoint recovery; the [validation record](validation.md#03-measurement-bounded-live-validation-2026-09-22-utc) states the coverage and remaining limits. No further live attempt is scheduled, and no 0.3.0 release tag or release-asset claim follows from this status.

Further live work should use one representative long chain and a small number of task-continuation checks with a declared request/time budget. Avoid repeated full offline matrices during routine iteration, keep only necessary evidence and remove regenerable scratch copies. A complete two-arm provider baseline remains deferred until sufficient budget is available. Cross-host and comprehensive multi-provider evaluation remain outside this scope. Extension migration is tracked separately, with each evaluated build and behavior change identified so later comparisons remain interpretable.

**Pre-1.0 public extension, development starts in the 0.3 period.** Deliver a package that users can install on unmodified Pi, configure and update independently of Pi itself. Plan against the 0.3/0.3.1 window first; the host-dependency work determines whether that window is achievable or a subsequent 0.x feature release is needed. If the scope exceeds a patch release, adjust the release numbering and sequence rather than reduce the deliverable to a feasibility report. Dependency mapping, a stock-Pi prototype, implementation, package verification and public release are steps toward this deliverable. Review the six host integration files against a pinned upstream release, identify public API replacements and necessary upstream interfaces, and resolve scope differences explicitly. Do not add a Pi distribution or host updater as a substitute.

**Instruction authority, a dedicated minor release, number assigned later.** A verbatim quotation proves that a source said something, not that the source may issue instructions. This release adds a mechanical distinction between sources that can produce instruction-level content and sources that can only produce evidence, informed by the instruction-authority failures that 0.3 measures. The contract must consider more than the message role: quoted or analyzed text inside a user message is not a user instruction, project rules have scope and can be revoked, and behavioral requirements can appear in any recovered section, not only under explicit instructions. Trusted-source labels are established by the host or a deterministic path, never claimed by the candidate note itself. The promise is bounded: prevent specified source classes from being mechanically promoted to instructions and test known confusion patterns; model adherence and semantic completeness remain outside it, as elsewhere. This gate precedes any experiment in which the session model writes its own increments.

**0.4.0, latency.** Move compaction work off the commit boundary by preparing increments while the task runs. Prepared increments are immutable, source-linked candidates: each states its frozen source range and hash, its branch identity and which user rulings it has processed, because an unchanged source hash cannot show that a later ruling made the content stale. The final candidate is still validated against the complete branch at commit time through the existing commit gate; a boundary without generation work is a fast path earned when prepared increments are complete and current, not a guarantee. Two preparation arms are compared under the same evaluation: background preparation with the same writer, evaluated first, and per-turn increments written by the session model. The second arm changes the model role whenever a fixed writer is configured and must be reported as an explicit configuration, not presented as a same-writer optimization. Preparation has its own failure lifecycle: a candidate invalidated by new input or a failed preparation call is a recorded, non-blocking event with its cost counted, a failed commit-time compaction keeps the existing blocking behavior, and cold starts or stale preparation fall back to the declared synchronous writer path. Evaluate a tiered writer separately; smaller-model increments are a candidate, not a committed implementation. Any model roles must be explicitly configured and reported, without silently substituting a writer on failure. Accepted when foreground pause falls while total task time, added per-turn latency, recovery quality and commit/failure guarantees hold, with an explicit budget covering all preparation costs, including session-model generation, validation overhead, session-file growth and measured cache behavior. Report discarded background work, stale-candidate rewrites and the distribution of pauses; list individual runs when there are too few samples for meaningful tail estimates. New user rulings and source changes must invalidate or update affected candidates before commit. If neither arm meets acceptance, the synchronous path remains and this optimization is dropped rather than weakened.

Scheduling needs a separate evaluation in a later 0.x release. **Hard compaction** pauses an unfinished task at a safe boundary, writes and commits a handover, then resumes the task. **Soft compaction** waits until the current task turn is complete before compacting. Automatic selection and adaptation between the two are future work; a threshold change alone must not be presented as support for in-task handover. Hard-compaction acceptance requires actual automatic checkpoints and successful continuation across at least two boundaries, preserving early constraints and distinguishing superseded decisions. Neither mode permits incomplete tool-call/result pairs or an uncommitted handover to reach the next request.

**0.5.0, note quality.** Note structure is revised from evaluation failures rather than from intuition, and history retrieval gains a typed index over decisions, file changes and errors so a model pages less. The index is a derived sidecar that can be deleted and rebuilt from the records; when it is missing, stale or untrusted, retrieval falls back to the existing search, and an index hit never widens branch or grant access. Accepted when recovery accuracy rises and average retrieval calls fall, with cold rebuilds, missed-entry probes and rebuild costs reported; fewer calls with lower accuracy is a failure, not a saving.

**0.6.0, footprint.** v0.2.3 brings forward source-size tiers, limited budget elasticity and serialized-note measurement to address daily failures. This milestone remains the evidence-based refinement of those initial parameters and writer overhead, not a second introduction of the same features. It also evaluates reversible reduction: removing already consumed or superseded tool results from the writer input and the active context as a view-level change while the originals stay in the session records. Stored originals alone do not make removal safe; eligibility rules must keep active requests, complete tool pairing and sole evidence for later decisions, and the cost of paging removed content back in counts against the saving. Accepted when token overhead falls while recovery accuracy holds.

**0.7.0 to 0.9.0, remaining integration and maturity work.** These provisional slots cover remaining interface work, broader compatibility and evidence needed for 1.0. Host changes required by the preview's supported workflows must already be eliminated or available in released upstream Pi before the preview ships; host changes cannot be hidden inside its installer. Improvements outside that initial scope can follow. Reorder these milestones around the public extension delivery and observed user needs. Preserve the guarantees promised by each release, and document any proposed scope changes and their consequences.

**1.0.0, mature independence.** Build on the public 0.x extension with a stable supported Pi/API range, a verified configuration/checkpoint compatibility and migration policy, repeatable recovery and failure-handling evidence, and a maintained install/update/remove path. Resolve outstanding limitations that prevent the agreed 1.0 workflows from being supported on unmodified Pi. Define the concrete 1.0 support matrix from preview evidence; neither all possible hosts nor every intervening version is required. First installability alone does not establish maturity, and users do not have to wait for 1.0 to use the independent extension.

## Evaluation contract

Recovery reports separate fact and exact-value accuracy, source support, superseded-decision handling, instruction authority and task continuation. A valid source ID or verbatim quotation does not establish that the source supports the claim or remains the current ruling. Include unapproved proposals and internal writer instructions so they cannot be mistaken for user authorization. Continuation checks cover the next task action, early constraints, repeated work and premature completion, alongside question answering.

Include questions whose answers are absent from the records. Report correct, incorrect and omitted or abstained answers, plus unsupported historical claims, with explicit counts and denominators. Distinguish unsupported claims from claims based on real but superseded or misinterpreted evidence. Report compaction failures and blocked continuations across all attempts, alongside recovery scores for completed probes; do not discard failed attempts or treat abstention alone as success.

Probe independent checkpoint copies so earlier probe answers do not leak into later ones. Pin and report fixture/scorer versions, host and compactor revisions, models, reasoning settings, budgets and tool access. Publish repeat counts and variation, not only the best run. Replayability means the inputs, procedure and scoring can be inspected and rerun; it does not promise identical model responses.

Ordinary CI checks fixture integrity, source mappings, scoring, report generation and deterministic regressions without provider calls. Explicitly triggered provider evaluations measure semantic recovery and live costs under a stated run budget. Scripted responses and replayed outputs are not new provider-quality measurements. Keep fixtures and scoring independent of the Pi runner where practical so the method can later evaluate other handover mechanisms; implementing another host is not part of 0.3.

## External baseline

The first recovery comparison is against Pi's native compaction on the same pinned Pi baseline, task model and replayable probe set. Reports must state compaction settings, retained-context budgets and allowed retrieval tools so the comparison can be interpreted. Provider-native compaction, where available, is an additional external baseline and is reported separately.

Once the native Pi comparison is stable, a same-host third-party compactor may be added. [Better Compact](https://github.com/AshishKumar4/better-compact) is a candidate, subject to compatible versions and the cost of a fair comparison; it does not block 0.3. Allow each compactor its documented recovery mechanism, report active-context size and retrieval cost, and accept verifiable source locations rather than requiring this project's entry-ID format. State budget differences instead of presenting unequal retained context as an equivalent comparison.

Whether source-linked compaction recovers tasks well enough to justify its pause, token and retrieval costs is still an open question. Reports will publish the trade-offs, including results that favor a baseline. Those results determine which parts of the project remain worth maintaining.

## Public extension delivery and acceptance

**Committed goal:** an independently installable, configurable and updatable extension on unmodified Pi, released for public use before 1.0. Pi remains maintained and updated upstream. This project maintains the extension, its dependencies and its declared compatibility. **Current status:** the existing implementation still requires host changes; the stock-Pi package has not been implemented. The existing source build supports development and comparison during migration, not a separate binary distribution product to expand.

Use Pi's Git/npm package facilities for installation and updates. A GitHub-hosted package is a valid initial channel; npm is optional. Document supported Pi versions, first-run setup, extension-only updates and how to select a newer pinned release. Preserve credentials, settings, sessions and other extension registrations. Do not replace the Pi executable, patch installed host files or rely on private host internals and call that independence.

The first public 0.x package must provide a useful end-to-end workflow: install on stock Pi, configure, compact into a source-linked note, retrieve supporting originals, resume the supported task/session, and update the extension independently. Verify source checks and failure behavior, plus disabling/removing the extension and compatible rollback. State which host versions, providers, session formats and workflows were tested. A preview can start with a bounded support matrix and documented limitations; it does not need every maturity criterion or optimization planned for 1.0.

Define the preview's supported scope and differences from the resident build before release. Core source integrity, user authority and explicit compaction-failure handling remain requirements within that scope. Broader resident-build guarantees, such as persistence across deliberate extension disabling or additional concurrency scenarios, must be assessed individually rather than silently promised or automatically imposed as preview gates. Describe unsupported workflows and their practical consequences. Existing custom sessions must either have a verified transition path or remain on their compatible implementation while the preview uses fresh sessions; installation never silently migrates original data.

The host-dependency review is the first implementation step, not the final deliverable. Where an upstream gap or a scope decision blocks progress, report the specific dependency, affected guarantee and proposed resolution. Adjust implementation, support scope or release timing explicitly; do not replace the public-extension goal with an open-ended investigation. Record preview evidence separately from resident-build results. Search rank, additional hosts and a separate Pi updater are outside this objective.

## After 1.0

Once the independent extension reaches 1.0 maturity, its default state is maintenance: patch releases for adaptation and a periodic run of the evaluation against native compaction. Three directions would justify further minor releases. One is portability, since the note, history and grant model does not depend on Pi and could serve other agent hosts through thin adapters. Another is a provider-native compaction payload as an optional acceleration layer, bound to model and tool-catalog fingerprints, falling back to the source-linked checkpoint on any mismatch and never replacing it as the authoritative recovery path. The third is a broader memory scope, which is explicitly outside the current design; adding it would change what the project is, and it would belong in a separate project or a second major release, decided at that time rather than assumed now.
