# v0.4.0 preview latency measurement specification

Status: P0 specification, `0.4-preview-latency.1`, now backed by a finite
synthetic runner. This document fixes the experiment and its reporting
requirements; executed results live in [validation.md](validation.md). It is
not a provider result, release acceptance or authorization for live calls.
The [implementation plan](v0.4.0-plan.md) defines dependencies;
the [roadmap](roadmap.md) retains the release requirements.

## Comparison dimensions and controls

Preparation strategy and observed commit path are separate axes:

| Preparation strategy | Meaning | Initial eligibility |
| --- | --- | --- |
| `synchronous` | No speculative preparation; declared writer works at `/compact` | Control |
| `A-background` | Configured writer prepares a cumulative candidate while the task runs | Opt-in experiment after P2/P3 |
| `B-session-increment` | Session model produces increments as part of task turns | Not eligible until the dedicated instruction-authority milestone passes |

| Commit path | Meaning |
| --- | --- |
| `complete` | Complete/current prepared candidate, no foreground generation |
| `prefix-conditional` | Historical candidate plus a complete raw tail, no foreground generation |
| `merge` | Declared writer reconciles a source-valid candidate with new input |
| `sync` | Original writer path; include the reason for unavailable/ineligible preparation |

A strategy can produce several commit paths. A failed attempt records its
selected path and failure, without becoming a successful hit. Report path counts
against all planned boundaries, and eligible-hit counts against explicitly
eligible boundaries; retain failed, blocked and unstarted boundaries in the
planned denominator. Do not label a `sync` fallback as a preparation hit.

Run fixed-writer and session-writer configurations separately. In session mode,
the background writer still uses the declared session model/prefix and is arm A,
not arm B. In fixed mode, B changes the preparation model role; report the task,
preparation and final writer identities individually. Smaller/tiered models are
a separate experiment, outside the initial comparison.

The primary comparison holds the source sequence, manual boundaries, actual cut
and retention policy equivalent between synchronous, A and eventual B. Compare
prefix submissions separately whenever they retain more raw history. Include the
additional input on later task requests: a shorter pause at a shallower cut is
not evidence of equivalent compression or lower whole-task cost.

Use one independent preview artifact per matched comparison on official npm Pi
1.1.0. Load a temporary copy outside any Node project, as the current acceptance
runner does. Persistent text sessions, one writing process, completed-turn manual
`/compact`, isolated settings and synthetic sources remain the initial scope.
Automatic hard/soft scheduling is not being measured.

Before execution, freeze a run manifest containing actual values:

| Field group | Required values |
| --- | --- |
| Identity | Measurement version; repository commit, dirty diff hash and relevant untracked-file byte hashes; preview runtime/build ID; built artifact SHA-256; package version; exact official runtime cohort package versions/integrities and installation lock hash; Node/OS/architecture |
| Evaluation | Scenario/fixture recipe version and byte hash; scorer/probe version; random seed, if any; declared run order; planned run/boundary/probe counts |
| Roles | Task model/provider/API and thinking level; configured writer selector; actual writer model/effort; preparation role; provider context/output limits |
| Policies | Complete latched extension config; Pi compaction settings; note tiers/floors; threshold/input allowance; retained-context/cut policy; custom instructions hash; cache policy; all experimental limits |
| Context | System/tool/prompt/schema identities; session-prefix identity where applicable; source sequence and safe manual boundary identities |
| Accounting | Ledger format/policy identity; usage field interpretation; cost currency/catalog version; reservation method; missing-usage policy |
| Resident reference | Current `eval/runtime.ts` pin and resident build ID, as reference fields only; frozen fixture/scorer identities remain distinct |

Do not invent a new model/build pin in this document or infer it from a historical
report. A field unsupported by the host/provider is `unknown` with a reason.
If inputs or policies change, start a new comparison identifier and manifest;
do not append incompatible samples to a previous baseline.

The [official-stock installer](../../scripts/context-memory-preview-stock-install.mjs)
pins the coding agent, chord, agent core, AI, codemode, MCP, TUI and telemetry
packages to the selected official release. Freeze its full cohort report;

Its SDK startup probe denies network access. This checks an unmodified official

## Finite synthetic baseline

The initial baseline comprises the following suites only. Use loopback/scripted
services, synthetic credentials and no provider endpoints. Scripted usage is
marked `synthetic`; it tests accounting and interfaces, not billed cost, prompt
cache behavior, semantic recovery or generation latency.

### S1: existing 20-checkpoint request-overhead loop

Use the existing `long-session-overhead` case in
[`context-memory-preview-scenarios.mjs`](../../scripts/context-memory-preview-scenarios.mjs)
with `--perf-checkpoints 20`. Keep its source text, 6,000-line trace recipe,
default settings, loopback responses and timing method unchanged for the first
baseline. Record the actual runtime identity before any optimization.

One process creates 20 manual checkpoints. It makes one initial source request
and two source requests per cycle: 41 construction task requests. At 10 and 20
checkpoints it makes three single-provider-request probes each; after reopening
the same session with the extension disabled, it makes three control probes.
Thus a complete run has 50 task requests, 20 compaction attempts, nine timing
samples and three reported medians. Writer/chunk/repair request counts are
reported separately, rather than assumed to equal the checkpoint count.

Preserve the existing calculation exactly:

- `extensionMs`: rounded median of three probe durations at each milestone.
- `baselineMs`: rounded median of three extension-disabled probe durations.
- `overheadMs = max(0, extensionMs - baselineMs)`.
- At 20 checkpoints, `overheadMs <= 50` milliseconds.
- Growth from 10 to 20 checkpoints satisfies
  `overhead20 <= 2 * max(overhead10, 5)` milliseconds.

The scenario's broader growth target is 10 to 60 checkpoints; this bounded P0
run does not establish that result. The two existing known gaps become required
checks only when the unchanged checks pass and the gap list is deliberately
updated. Preserve all raw probe durations in new instrumentation; do not claim
nine independent sessions or estimate a reliable P95 from these nine probes.

After the shared validator is reviewed, repeat S1 once on that candidate build.
If the target fails, retain the failure and profile remaining work; do not skip
disk reads, quotations, old checkpoints or request hooks to meet it. Additional
runs require a declared reason such as a changed implementation or unresolved
measurement noise.

The final shared candidate's inconsistent S1 measurements justify one declared
diagnostic run before further changes: run the existing long-session worker once
at 20 checkpoints, bounded to 70 synthetic loopback HTTP calls and 180 seconds,
on the exact final artifact after other CPU checks finish. Collect the worker's
Node CPU profile (1,000 microsecond sampling), GC trace and original monotonic
probe intervals; retain the profile and result before deleting scratch sessions.
Align samples inside the nine real request intervals rather than treating the
whole chain as ordinary request work. This is diagnostic evidence, not another
acceptance comparison or a replacement for either existing S1 failure. Detailed
component/operation counters remain a subsequent instrumentation experiment if
the aligned profile cannot identify a concrete optimization.

That component experiment now has a finite source-bound harness,
[`context-memory-preview-request-profile.mjs`](../../scripts/context-memory-preview-request-profile.mjs).
It runs the same worker once with 20 checkpoints, 70 loopback admissions and a
180-second parent deadline. A temporary instrumented package is built from one
verified source snapshot, with exact source anchors and byte-identical baseline
artifact checks; the production package and acceptance calculation are unchanged.
It records at most 210 hooks in a 3 MiB content-free journal, with 16 KiB records
and bounded worker output. Timings use an owned stack to partition each hook into
inclusive/exclusive wall time and unattributed remainder. Count serialization,
hash updates, prefix boundaries, observer collection, whole-branch plain-data
proof, full-file read/decode/scan, canonical comparisons, metadata, parsing and
fallback hashes. `serializedCodeUnits` means UTF-16 code units; `diskBytes` means
actual UTF-8 file bytes. New byte encoding or comparison must receive its own
timer/count rather than disappear into another stage.

Preserve partial journals and bounded diagnostics on timeout/failure, then delete
scratch sessions. Retained reports contain no session text or identifying paths.
Instrumentation and per-admission logging add work; its latency medians are
diagnostic and cannot replace S1 acceptance. Report each artifact and instrumenter
identity separately. A changed runtime may justify one further component run;
unchanged failures do not justify retries for a better result.

### S2: two manual checkpoints and independent continuations

Specify one new, deterministic synthetic chain for each writer mode, then freeze
its source bytes and boundary/cut preflight before execution. This scenario is
not implemented by S1. Its runner and executed results are linked from the
[validation record](validation.md#s2-matched-synthetic-execution).

Each chain starts with one synthetic task/source turn, followed by two cycles.
Each cycle has one task/ruling turn and one trace turn using S1's trace recipe,
then an explicit completed-turn `/compact`. There are five construction task
requests and two planned checkpoints per chain. The oracle fixes an early
restriction, an exact value, a later superseding value, a revocation and already
completed work that must not repeat. A later ruling occurs after the first
checkpoint and before the second; the safe cuts and which originals they release
are fixed in the preflight. Synthetic filler is not scored evidence.

At each committed checkpoint, reopen in a fresh process and run three independent
probes from separate snapshots: (1) exact value plus source support, (2) current
permission/revocation, and (3) actual next action without repeating completed work.
The first two permit one provider request each. The action probe permits at most
two actions and three tool rounds, with at most four provider requests. Each
probe has its own task state and cannot inherit another probe's answer. Reserve
six probes per chain even if a failed checkpoint blocks their execution.

The initial synchronous baseline is two chains total: one fixed-writer and one
session-writer configuration, four planned checkpoint boundaries and 12 planned
independent probes. Across the two chains, the ceiling is ten construction task
requests plus 24 probe provider requests. Report actual counts and blocked or
unstarted probes, not just this ceiling. Scripted writer/probe responses exercise
restoration and scoring interfaces; their semantic answers are not model evidence.

After A exists, run the same two chains with the same preparation-eligible points.
Declare dispatch relative to completed turns, including whether a new ruling
arrives after preparation. Before interpreting path hit rates, add separately
named deterministic cases for complete reuse, a new ruling requiring merge,
cold start, stale source, cancellation and missing usage. These regression cases
do not expand the two-chain semantic/provider sample count. Prefix cases remain
disabled until their contract gate passes. B uses the same frozen chain only
after its authority gate and a newly declared budget.

## Initial experiment limits

These ceilings are enforced for preview preparation when explicitly enabled;
the experiment is off by default and authorizes no live spending. Foreground
limits below belong to the finite S2 harness, not a new restriction on ordinary
manual compaction. The runner validates a complete experiment policy before
dispatch; its synthetic override of the five-second interval is in the manifest.

| Limit | Proposed initial value |
| --- | --- |
| Preparation attempts | One per checkpoint interval; two per two-checkpoint chain |
| Preparation concurrency | One in flight per session; coalesce notifications |
| Preparation calls | At most eight generation/chunk calls per attempt; zero size-repair calls; zero transport retries; 16 calls per chain |
| Foreground writer calls | At most eight generation/chunk calls plus one same-writer size repair per boundary; 18 calls per chain; zero transport retries |
| Prepared candidates | One completed cumulative candidate plus one running immutable envelope; at most 24,000 bytes of serialized note per completed candidate, still subject to the actual note policy |
| Trigger interval | Completed turns only; at least five seconds since the prior dispatch and 2,048 new source-proxy tokens; no per-turn paid restart on freshness loss |
| Deadlines | At most 120 seconds per preparation attempt; 600 seconds per foreground attempt; 30 minutes per chain including probes |
| Preparation token reservations | 1,200,000 input/output/cache token units per interval; 2,400,000 per chain, using the declared provider field interpretation |
| Preparation spending reservations | USD 1.00 per interval and USD 2.00 per chain; unknown price prevents live optional dispatch |
| Foreground/probe reservation | Separate limits must be declared in the run manifest before any live run; preparation ceilings never authorize them |

Each chunk, repair and retry is a distinct call reservation, even when one
`writeMemory` invocation produces several requests. Usage exceeding a reservation
halts further optional dispatch and is reported. Unresolved cancelled/interrupted
calls continue to consume their reservation; reload/restart must not reset it.
The 20-checkpoint S1 suite is synthetic and uses its own finite 20-boundary
envelope, not an enlarged live two-chain allowance.

Freeze each call's input reservation and output/reasoning allowance from the
actual model/payload before dispatch. The aggregate limits above do not replace
provider context limits or the note policy. Unsupported chargeable internal
retries or missing request visibility are accounting gaps, not free calls.
Any change to these limits requires a new manifest before testing. Runtime call
reservations conservatively use the declared model context capacity plus output
allowance and the maximum applicable catalog input/cache rate. They are budget
guards, not provider billing or a claim about text-estimator accuracy. Pi's
returned cost fields are catalog estimates. Interrupted positive usage is a
lower bound with `usageComplete: false`; default-zero interrupted usage stays
unknown. Optional reasoning and one-hour cache-write splits remain unknown when
absent, and neither subset is added again to total tokens.

## Prospective provider exercise

Provider work is deferred. Once separately authorized and P2/P3 accounting is
ready, start with one writer mode and one matched synchronous/A pair of S2
chains, rather than a full matrix. That is two chains, four planned boundaries
and 12 planned probes; list individual outcomes. Freeze the actual task/writer
models, source/cut preflight and cache policy before dispatch. Run fixed and
session modes as separate later exercises; do not pool them. B needs its own
authorized envelope after the authority gate.

For this prospective pair, the specimen ceiling is 34 ordinary/probe provider
requests, 36 foreground generation/repair calls and 16 preparation calls: 86
calls maximum, with at most 30 minutes per chain. This is an upper bound, not
a recommended spend or permission to use it. The authorization must set a
whole-exercise currency/token ceiling covering all three categories and may set
a lower request limit. A missing foreground/probe cost envelope prevents live
execution, even if the optional preparation budget has been specified.

Stop on the first reached request/time/spending ceiling, unobservable charged
retry, unresolved accounting gap, integrity failure or blocked continuation;
preserve consumed costs and remaining unstarted work. An exhausted preparation
budget stops optional dispatch but does not invalidate a healthy synchronous
path. A failed formal compaction still blocks the next task request. Do not
replace failed calls, switch models or raise limits inside a run. Provider
results supplement synthetic regressions and do not relabel them as live.

## Required observations and formulas

Keep content-free summaries outside the repository. Do not store transcript or
note text, credentials, raw provider errors or identifying local paths in reports.
Controlled IDs and hashes may link summary records to local scratch evidence.

| Record | Required observations |
| --- | --- |
| Run | Planned/started/completed/failed/blocked/unstarted chains, checkpoints and probes; exact samples; cold-start/restart state; total task wall time; ordinary task latency with and without background work |
| Boundary | Preparation strategy; selected commit path and reason; candidate/parent/base checkpoint/epoch; complete/current/prefix eligibility; custom-instruction compatibility; wait/generation/validation/stage/disk-confirmation durations |
| Sources | Full commit branch leaf and ordered membership hash; frozen candidate covered-through and prefix hash; released/retained membership and safe cut hash; actual `firstKeptEntryId`; processed user-entry horizon; source projection before and after reopening |
| Artifact | Serialized note bytes/hash; rendered summary bytes/hash; lineage footprint; budget tier/base/hard limit; source/released/retained proxies; actual context before/after; checkpoint ID/hash and disk-confirmation result |
| Every call | Controlled call ID; actual model/effort; task/preparation/merge/sync/repair/retrieval/probe purpose; dispatch/terminal times; reservation; outcome; returned usage availability; reuse/discard/supersession links |
| Usage | Ordinary task input/output/reasoning/cache-read/cache-write fields as well as writer fields; per-field known/unknown status; returned totals and their provider interpretation; usage-report count versus dispatched count |
| Accounting | Durable ledger completeness, unresolved reservations, duplicate/cumulative settlement handling, rotation/export window and `costLedgerGap`; known discarded work and stale rewrites; returned cost versus catalog-estimated cost |
| Storage | Session bytes/growth, ledger/detail/aggregate bytes, candidate memory bytes, validation CPU/wall time and background contention |
| Recovery | Fact/value, source support, supersession, authority and actual action verdicts separately; repeat/forbidden action counts; stop reason; error class; blocked/unstarted denominator |

Hash definitions must be explicit. Branch/prefix hashes preserve the current
SHA-256 stream of `JSON.stringify(entry)` followed by `"\n"` for each entry in
order. For a cut, record hashes of the corresponding ordered released and
retained original-entry sequences, their IDs and the boundary decision; a raw
entry index alone does not prove complete projected coverage. Artifact hashes
use exact UTF-8 serialized/rendered bytes. Deterministic fixture recipe hashes
and realized per-run entry hashes are distinct because session IDs/timestamps
may differ. Record them, rather than forcing different runs to share entry IDs.

Use monotonic timestamps within each process and follow the existing
[`0.3-measurement.2` timing contract](../../eval/measurement-contract.json):

- `compactionMs = commitComplete - trigger`.
- `orchestrationMs = recoveryDispatch - commitComplete`.
- `resumeRequestDelayMs = nextTaskProviderRequest - recoveryDispatch`.
- `pauseMs = compactionMs + resumeRequestDelayMs`.
- `rawBoundarySpanMs = nextTaskProviderRequest - trigger`.

Immediate recovery dispatch excludes harness orchestration from `pauseMs` but
always reports it. Nested phase times must not be double-counted. On failure,
record time to failure/block; there is no successful resume/pause value.
Background time is measured from dispatch to settlement and separately reports
how much overlapped task work or caused foreground waiting.

Report total ordinary task usage plus all preparation, foreground, repair and
retrieval usage, including failed/discarded calls. Reusing a candidate does not
charge its generation twice. For B embedded in an ordinary response, count the
whole provider report once and use the matched whole-task difference; do not
invent an exact task/increment token split. Provider cache fields are mandatory
observations for the session writer but may be unknown. Stable prefix text does
not prove a hit; report cache reads, writes and any known charges.

Returned usage, host/catalog cost estimates and measured billing are separate
columns. A synthetic zero cost is not a live measurement. Missing usage/cost is
`null` with missing-call/field counts, never silently zero. A ledger gap prevents
a complete-cost or cost-saving claim. Unknown charged usage is accompanied by
its reserved upper bound, without presenting that bound as returned usage.
The preview ledger observes Pi SDK-normalized usage. Its completeness flag does
not certify that the raw provider exposed cache/reasoning breakdowns or billed
cost; the S2 runner retains independent raw-field availability. Do not relabel
SDK defaults as provider evidence.

Released source uses the existing proxy: sum `ceil(UTF-8 source bytes / 3)` over
currently active original records actually removed, excluding previous notes
and already archived originals. Preserve distinct provider/tokenizer estimates.
Report writer overhead against actual released source, recovery footprint and
retrieval overhead with the existing formulas. Failed attempts release zero;
ratios with zero denominator are `null`. Prefix-path retained-tail footprint and
subsequent task input appear beside its pause, not hidden inside a pooled median.

## Acceptance and integration decisions

For P1, the exact existing 50 ms and bounded-growth checks above are targets;
no additional numerical latency promise is established here. For A/B, freeze
allowable whole-task time, added turn latency and total-cost limits before a
live comparison, then report every individual boundary/probe in these small
samples. A lower pause alone is insufficient. Recovery has no accepted regression
against the matched synchronous control; source, commit and failure regressions
remain hard gates. Do not infer tail percentiles or general quality from two
chains per strategy.

The shared single-pass validator preserves identical hash bytes and the existing
quote/schema/supersedes/budget checks. Each preview request guard produces a new
canonical-line map and consumes it immediately in the same synchronous frame.
The store rereads the complete disk file and failure marker, checks every entry's
metadata and ancestry, and reuses an in-memory entry only for an exact canonical
line containing plain data. Nonstandard objects, differently formatted lines
and repeated map use take the existing parse/hash path. No cross-request cache
or cross-hook reuse is used. Equivalence, same-leaf tamper and future-reference
regressions are required alongside performance evidence.

Shared `notes.ts`/`identity.ts` affect the resident stamp and frozen evaluator.
The maintainer authorized preparing these shared changes and their candidate
fingerprint for review, without committing. The frozen pin remains unchanged:
it requires an actual implementation commit before the separate pin update.
The [operations gates](operations.md#two-deliberate-gates) still apply; do not
bypass `EVAL_FROZEN_INPUT_CHANGED` or represent a working-tree hash as that commit.

`prefix-conditional` remains disabled until the historical/temporal contract,
instruction precedence, complete raw-tail/tool-pair projection, positive release,
full-branch versus covered-prefix markers, disk confirmation and reopen/rollback
tests pass. A retained newer ruling is evidence, not proof that old note
instructions were reconciled. A new custom `/compact` instruction defaults to
generation unless explicitly shown compatible. Arm B remains disabled until the
dedicated instruction-authority gate mechanically addresses trusted provenance,
quoted user content, scope, revocation and behavioral content in every section.

No preparation failure enters `controller.fail()` or `store.begin()`, and no
successful path weakens the durable commit gate. Candidate lifecycle/cost failures
are recorded without blocking a healthy task; actual compaction failure preserves
the existing request block. If the optimization misses its declared performance,
quality or cost limits, retain synchronous behavior and report the failure.
