merged. The [release scope](v0.4.0-release.md) and [extension guide](extension-preview.md)

## Scope and current evidence

Keep official Pi 1.1.0, persistent text sessions, one writing process and manual
`/compact` as the initial delivery scope. Automatic hard/soft scheduling remains
a later milestone. Additional host versions, attachments, parent grants,
historical-session migration and competing compactors require their own evidence.

The current preview already exposes `context_note`, but those notes are optional
suggestions without a preparation envelope. They remain inputs for foreground
writer reconciliation when generation is needed; an eligible completed
preparation candidate is a separate artifact. Reuse the validation and writer
logic rather than treating existing note increments as completed preparation.

The [v0.3.3 validation record](validation.md#v033-existing-session-compatibility-2026-10-12-utc)
reports approximately 358 ms per request at 10 checkpoints and 1,153 ms at 20 in
a synthetic environment. Repeated prefix serialization/hash checks dominate
the profile. These are request-side costs, not provider generation latency.
The existing scenario targets are 50 ms of extension overhead per request and
bounded growth. At that baseline both targets were known gaps. Growth was promoted
to a required check after an earlier standalone pass; the latest hardened
candidate fails it in both standalone and complete runs. The 50 ms target remains
a known gap. Neither target is accepted yet.

Superseded on 2026-10-13 by D15: with full validation at trust boundaries, the
strict long-session scenario measures 1–4 ms extra median overhead at 10 and
20 checkpoints, and the 50 ms check is now a required regression. The first
request after each boundary still pays one full check; see the
[validation record](validation.md).

There is no measured natural preparation fast-path hit rate. `/compact` itself does not
establish that a new user message was appended; the interval between preparation
and submission determines freshness. Both frequent and rare full-candidate
reuse are hypotheses to measure. Smaller tail input can shorten a fixed-writer
merge, but the session writer still uses its current provider prefix. Neither
mode has a demonstrated latency or cache benefit from this change.

## Candidate contract

A preparation candidate must carry a cumulative note: the base checkpoint plus
all newly represented projected originals through its coverage boundary. Delta
fragments cannot become a checkpoint by concatenation. Candidate metadata is
selected by deterministic extension code, never self-certified by the model.

Freeze the input envelope when preparation starts:

- Candidate and parent-candidate identifiers, session identity, preparation
  epoch, base checkpoint and frozen branch ancestry.
- The original source range, ordered source membership and prefix hash,
  `coveredThrough`, and which user entries/rulings were supplied and processed.
- The selected writer model and reasoning level, generation policy, schema and
  prompt identity, and relevant system/tool context identity for a session writer.

On successful completion, validate and freeze the cumulative output note, actual
writer/call metadata and accounting links. Bind input and output with the
candidate identifier and their hashes. The output note does not exist at dispatch;
generation cannot modify the frozen input envelope or its source horizon.

Separate the full branch snapshot used for commit integrity from the prefix
represented by the note. A commit can have a later full-branch leaf/hash than
the candidate's coverage endpoint/hash. Both require validation. A retained tail
does not permit weaker disk readback of the full branch or checkpoint parent.
All candidate `sources` and `supersedes` references must resolve inside its
frozen covered prefix, including originals represented by the base checkpoint;
they cannot cite a later tail protected only by the submission snapshot.
The processed-input horizon attests which originals the writer received, not
that the writer semantically preserved every ruling.

Use distinct eligibility checks:

1. **Valid for its frozen sources:** those sources and the base checkpoint still
   match, the ancestry is correct, and note references and quotations validate.
2. **Current as a full handover:** all required sources and later user rulings
   have been reconciled into the candidate.
3. **Eligible as a historical prefix:** the separate retained-tail contract has
   passed, and everything beyond its coverage remains in the final projection.

Every new user entry conservatively invalidates full-handover freshness. Keep a
still-source-valid candidate available for a same-writer merge; freshness loss
does not require throwing away all prior preparation. Reuse as a historical
prefix is conditional, rather than an automatic exception for new rulings.

Candidate budget compatibility is a bound check. Recalculate the note policy
from the content actually released at submission, and require the serialized
note to fit that policy's hard limit and the final context allowance. Different
preparation and submission tiers do not by themselves invalidate the candidate.
Writer-role or prompt changes that affect provenance require separate checks.

## Commit path selection

At `/compact`, freeze the current branch, select a safe cut, establish the current
note policy, and classify candidates before selecting a path. Use the same final
validation and durable commit gate for all paths.

| Path | Eligibility | Foreground generation | Required measurement |
| --- | --- | --- | --- |
| Complete candidate | Candidate is complete, current, source-valid and compatible with submission requirements | None | Hit rate, pause, validation time and released context |
| Historical prefix with raw tail | Prefix contract is enabled; a safe cut releases only represented content and keeps all later projected originals | None | Hit rate, pause, retained/released context and recovery under later rulings |
| Same-writer merge | Candidate is valid for its original sources, but additional sources or submission instructions need reconciliation | Merge/rewrite with the declared writer | Tail size, input/output/cache usage, pause and preparation reuse |
| Synchronous path | Cold start, unavailable preparation, untrusted/invalid candidate, budget mismatch or no eligible prepared path | Existing declared writer path | Reason, pause and total cost including prior preparations |

Custom `/compact` instructions received only at submission default to generation
unless an explicit compatibility check proves they were already satisfied.
They cannot be ignored to obtain a zero-generation result. If no path can produce
a valid handover, retain the existing blocking compaction failure behavior.

### Historical prefix with raw tail

The note validator accepts a `coveredThrough` before the current branch leaf,
and stock Pi can retain entries starting at `firstKeptEntryId`. The preview's
failure store currently requires checkpoint coverage/hash to equal the complete
attempt leaf/hash. Partial-prefix submission needs an explicit contract change
in controller, staging and disk confirmation; schema permissiveness alone is
not sufficient.

The proposed path must satisfy all of the following:

- The cut is no later than the represented prefix boundary and is a valid
  projected turn/tool boundary. If it moves earlier, the extra raw content is
  retained without creating broken tool-call/result pairs.
- The candidate represents everything omitted from the active projection,
  including the preceding checkpoint's state. No source or unprocessed ruling
  disappears between the previous handover, candidate coverage and retained tail.
- The note is visibly and mechanically scoped to its covered historical prefix.
  Later retained originals remain chronologically later and supply the current
  rulings and progress. Existing `instructions`, `state` and `nextSteps` must not
  silently claim to describe the whole current branch.
- The final note plus retained originals, system state and tools fit the recovery
  threshold and actual provider input allowance. It achieves positive measured
  context release and does not just append an equally large checkpoint.
- The full submission branch, note prefix, safe cut and exact checkpoint are
  staged and confirmed from disk. Reopening reconstructs the same projection.
- Later-ruling, revocation and completed-step probes demonstrate that the model
  follows the retained tail rather than repeating obsolete note instructions.

Keeping the raw newer ruling gives the model evidence; it does not mechanically
establish semantic reconciliation. This path therefore remains a conditional
experiment until the temporal/authority contract passes. If it cannot meet the
roadmap's requirement to invalidate or update affected candidates, use the merge
path, or make the proposed roadmap refinement an explicit maintainer decision.

Before integration, decide how expanded coverage is represented in checkpoint
details and attempt markers. Preserve existing checkpoint reading, define
unsupported new data as fail-closed, and test pending/staged recovery across
update and rollback. Do not infer rollback compatibility from unchanged global
schema numbers; the current marker parser rejects unexpected fields.

## Preparation lifecycle and budgets

Use a preparation coordinator under `preview/` with its own immutable snapshots,
epoch and AbortController. Bind it to session teardown, reload and navigation;
do not borrow a future compaction event's signal. Public completed-turn or
completed-tool-batch events can enqueue bounded work without awaiting generation
in the task's request path.

The preparation states are idle, running, ready, stale, failed, cancelled and
discarded. They are separate from commit pending/blocked state. In particular,
preparation never calls `controller.fail()` or `store.begin()`. Those operations
have sticky request-blocking effects. Actual submission still uses the existing
begin, stage, Pi append and disk-confirmation sequence.

Freeze configurable limits before testing:

- At most one preparation call in flight per session; coalesce further source
  changes instead of dispatching competing calls.
- A minimum amount of new source, a debounce/minimum interval, and a maximum
  number of calls between checkpoints and per session/time window.
- Input/output/reasoning token reservations, wall-time deadlines and aggregate
  preparation spending limits, including repairs and discarded work.
- A maximum candidate count/size and an explicit policy for retiring candidates.

Start conservatively with one preparation attempt per checkpoint interval and
explicitly opt-in preparation. Raise the limit only in a declared experiment
whose cost and hit-rate results justify it. Count transport retries and size
repair calls against the same budget. Session restart/reload must not reset
spent reservations or create an unbounded retry loop.

New user entries revoke full-candidate eligibility immediately but need not
trigger a new paid call immediately. An ordinary append can leave the frozen
prefix intact: its completed result may be kept as a source-valid stale candidate
for a later same-writer merge, never as a current full handover. Branch/session,
base-checkpoint, configuration or source-integrity changes invalidate the relevant
epoch or source identity; abort that work where possible and discard mismatched
late results. Settle costs even if usage arrives only after cancellation.
A preparation error does not clear an existing commit block. Source corruption
discovered by ordinary request guards still follows the existing blocking
integrity contract.

## Durable preview cost accounting

Add a preview-local, bounded content-free preparation journal with atomic
aggregate counters. In-memory `lastProgress`, checkpoint usage and scenario
observations alone cannot account for discarded work across restart. Prepared
content can be deleted and rebuilt; observations of paid calls cannot be
reconstructed from the transcript.

Persist a dispatch reservation before each optional preparation call. Record
controlled identifiers, actual model/effort, purpose, elapsed time, outcome,
usage availability, cache read/write usage and reuse/discard links. Never record
transcript text, note content, credentials, raw provider errors or local paths.
Expose aggregate counters, remaining budgets and observation gaps through
`/compaction-status`; the scenario/evaluation runner consumes the same records.

Writer progress reports are cumulative. Settle idempotently by call identifier
and monotonic totals rather than summing every callback. Calls can be recorded
once while their artifacts are reused, superseded or discarded later. Count
preparation, foreground merge, synchronous fallback and repair as separate cost
categories; never charge reused preparation a second time at commit.

On restart, an unresolved dispatch becomes interrupted with unknown usage. It
remains charged against its reservation until a trustworthy report resolves it;
unknown is never zero. Rotate detailed records only after their accounting has
been durably folded into bounded aggregate state, retaining the comparison
window or exporting its content-free summary before rotation.

If reservation/accounting cannot be trusted, pause optional preparation, expose
an observation gap and use the normal synchronous path. Logging failure must
not invoke commit-failure markers or block otherwise healthy task requests.
Incomplete accounting disqualifies a cost-saving claim, even if latency falls.

Measure provider cache behavior as a required result for the session writer.
Preserve its intended prefix and report actual cache reads, writes and costs;
do not infer cache hits from identical text. Additional calls can increase cache
write charges or contend with task requests. Mark missing provider usage/cache
data as unavailable and distinguish catalog estimates from measured billing.

### P1 Reduce repeated request validation

Current implementation, functionally validated with performance gates incomplete:

- Shared `hashEntryPrefixes` serializes entries in order and copies SHA-256 state
  at required prefix boundaries, preserving `JSON.stringify(entry) + newline`.
  Shared `validateMemoryCheckpoints` checks every checkpoint oldest first with
  invocation-local source, prefix and continuation indices. Historical lookup
  remains bounded by each checkpoint's existing permitted source range, while
  public `latestMemory` keeps its latest-only behavior. Schema, quote, supersedes,
  stored-budget and restored-summary checks remain in the shared validation path;
  new candidates additionally enforce their own coverage boundary.
- Preview `assertReady` first proves that the entire branch is side-effect-free
  plain data and that required metadata survives serialization as own enumerable
  data. Its prototype descriptor tables and ancestry must match the trusted
  module-initialization baseline; later inherited getters or serializers take
  the ordinary path. This assumes trusted Node intrinsics at module load, not a
  sandbox against arbitrary local code. It then collects each freshly serialized canonical line as UTF-8 bytes
  with its current branch object. The failure store consumes only a complete
  factory-owned collection in the same synchronous frame, with no intervening
  await or handler dispatch. The caller must not mutate or retain the objects or
  byte collection between serialization and readback. Snapshot and collection
  are each consumed once; unowned, incomplete or reused proof takes ordinary
  independent parsing and hashing.
- Each invocation still reads the complete JSONL from disk and checks the fresh
  marker, header, entry metadata, duplicate IDs, root count and parent chain,
  including off-branch entries. Exact canonical lines for plain data can reuse
  their corresponding branch objects. Full-file byte scanning preserves physical
  record limits and the legacy per-line lossy UTF-8 parser for every fallback;
  sibling records remain validated even when interleaved with selected ancestors.
  Only when the selected disk branch has
  exactly the current branch objects in order can it avoid reparsing those lines
  and recomputing disk/memory branch hashes. Other formatting, unmatched lines,
  changed branches and non-plain values, serialization hooks, accessors or proxies
  take the ordinary parsing/hash path. Status, inspect and durable commit
  confirmation retain their existing independent readback behavior.

Each request hook independently performs this fresh validation. There is no
cross-hook or cross-request serialization cache. The three public request events
do not provide a shared request identifier, and other handlers may run between
them. Any future cross-hook reuse requires a proven request epoch and invalidation
protocol, including same-leaf edits between hooks. The final payload guard remains
independent. If the current algorithm cannot meet the target, retain the failure
and profile the remaining costs rather than weakening detection.

pin advancement remains blocked until implementation commit C1 exists; final

deterministically; reservations survive restart; cumulative callbacks cannot
double-count; log failure keeps normal requests usable; old checkpoints remain

### P3 Implement background preparation with the configured writer

Add the coordinator and bounded scheduling through public extension events.
Reuse the configured writer with no model substitution. A fixed writer can
merge a cumulative candidate with new source chunks and referenced originals;
a session writer retains its declared provider-prefix behavior. Report these
writer modes separately. Verify frozen system/tool identity and cancellation.

Completion: preparation does not await generation in the task request path;
call/spending limits hold across reload/restart; stale results never publish as
current full handovers and identity-mismatched late results are discarded;
source-valid prefixes remain available for merging; failure/cancellation settle
accounting without commit markers; cold starts remain usable through synchronous
compaction.

### P4 Implement commit selection and conditional retained-tail reuse

Integrate complete-candidate reuse, same-writer merge and synchronous fallback
through the existing commit gate. Add historical-prefix submission only after
its contract tests and scope decision. Validate the actual source coverage and
post-compaction projection, not just a raw entry index inequality. Custom
instructions and current budget limits remain enforced.

Completion: each path has an observed reason and correct cost attribution;
zero-generation paths make no writer call and still confirm the full branch and
checkpoint on disk; failed staging/append/confirmation remains blocking; explicit
retry and recovery retain their existing distinctions.

### P5 Evaluate session-model increments after the authority gate

Track the dedicated instruction-authority milestone as a dependency. Its
trusted provenance labels must come from the host or a deterministic path and
cover behavioral content in every note section, including quoted user content,
scope and revocation. Do not treat exact quotation or `role=user` as sufficient.
The [authority design](archive/instruction-authority-design.md) defines the proposed
mechanical gate and negative matrix. Its explicit intake experience, supported
origin path and new checkpoint/projection compatibility require proof; these
are not already implemented by the candidate source horizon.

D9/D10 select the prototype direction. The unused ownership primitive passes 66
focused checks, its public guard installer 13, and official SDK refusal exercises
21 expected classified cases. Public bootstrap covers both source-free stock
initialization prefixes, first flush and interrupted replacement; it is synthetic
UI mechanics, not trusted human admission. The current shipped preview graph is
unchanged. See the [separate evidence](validation.md#unreleased-authority-bridge-and-public-api-prototypes).

Next, implement a bounded interactive-review prototype with exact original text
block/UTF-8-span partitions, adopt/replace/revoke/data receipts, fresh native-entry
and disk binding before provider dispatch, and host-only active-set replay. Prove
the same evidence projection for every model note field, lineage, continuation,
ordinary input and opaque prompt origins. Interrupted first enrollment must leave
a content-free failure sentinel in the supplied setup manager; private latches
cannot protect a replacement reader. Keep unclassified input, missing receipts,
unsupported prompt contributors and navigation blocked. Do not mistake ownership
`active` for authority readiness, or a model quotation for user adoption.

After it passes, configure and measure session-model per-turn increments as arm
B. When a fixed writer is configured, make the changed preparation role explicit.
A separate background call to the session model in arm A is not arm B; define how
per-turn increments are produced and charge any added generation/tool overhead.
If generation shares an ordinary task response, report the complete provider
usage and matched whole-task difference. Do not invent an exact split between
task and increment tokens when the provider supplies only a combined report.

Completion: authority regressions pass, actual model roles are visible, and A/B
use the same declared evaluation. If B is deferred, require an explicit roadmap
scope decision before calling the original v0.4.0 comparison complete. Smaller
or tiered writers remain separate experiments.

## Evaluation and release gates

Preparation strategy and commit path are separate dimensions. Keep the existing
project/native evaluator identity meaningful; add a preview-specific measurement
version rather than relabeling historical arms or moving the resident pin to
make new tests pass. Reuse inspected fixture/scorer methods where appropriate.

Compare synchronous, configured-writer background preparation and gated
session-model increments. For the primary generation comparison, keep cuts and
retained-context budgets equivalent. Report historical-prefix submissions as a
separate trade-off when their cut retains more raw history. A shorter pause from
releasing less context is not an equivalent compression result.

| Gate | Evidence required |
| --- | --- |
| Foreground pause | Pause from trigger to next request, split into waiting, generation, validation and commit; path counts, fast-path hit rates and per-run distribution |
| Everyday latency | Request overhead at checkpoint milestones and added task-turn latency; both existing stock-Pi overhead checks pass |
| Whole-task performance | Total task wall time, background contention and cold-start/stale-preparation behavior, within predeclared limits |
| Recovery | Fact/exact value, source support, superseded decisions, authority and actual next actions reported separately; no accepted regression against the matched synchronous control |
| Complete cost | All task/session-model input/output/cache usage plus known and unknown preparation, merge, fallback, repair and retrieval usage; discarded/repeated work, actual cache behavior, journal/candidate/session storage and validation overhead |
| Persistence and failure | Every successful path confirms checkpoint and full branch from disk; all failed submission paths preserve blocking and explicit recovery rules |
| Distribution | Independent build/install/update/remove, fresh-process reopen and declared rollback cases on official Pi, outside repository module resolution |

Use a representative chain with at least two manual checkpoints plus a small set
of independent continuation probes. Include a later ruling/revocation and
completed work that must not repeat. This measures latency and freshness, not
new automatic scheduling support. Report every run when sample size is too small
for meaningful tails. Keep failures, blocked continuations and unstarted runs
in their declared denominators.

The deterministic regression matrix must cover:

- Full/prefix source hash equivalence, cross-branch candidates and historical
  checkpoint/source tampering, including edits that preserve the leaf.
- New user rulings, changed values, revoked scope and later completion of steps;
  raw-tail preservation and correct chronological projection after reopening.
- Missing coverage, invalid safe cuts, incomplete tool pairs, insufficient
  context release, oversized retained tails and submission budget tier changes.
- Custom compaction instructions, writer model/effort and system/tool changes.
- Preparation cancellation, provider failures, late results, session switching,
  reload/teardown, restart orphans, exhausted budgets and missing candidates.
- Exactly-once/cumulative accounting, unknown usage, duplicate settlement,
  journal rotation, reservation failure and terminal accounting failure.
- Zero-generation submission with disk confirmation; stage/append/confirmation
  failure, interrupted recovery and incompatible update/rollback markers.
- Any proposed cross-hook reuse under retries, nested/reentrant hooks, source
  changes between hooks and final payload removal/replacement.

Ordinary implementation validation follows
`node scripts/context-memory-ops.mjs verify`, preview build, isolated stock-Pi
acceptance and default-settings scenarios. Full CI uses the runbook's `ci`
sequence after any shared-runtime freeze decision has been resolved. Do not run
`npm test`, the full upstream suite or live tests with unapproved credentials.
Record the command, exit code and actual scope for every validation claim.

If a preparation arm does not lower pause within the declared total-time,
per-turn, cost and recovery limits, keep the synchronous path. Reject a retained
tail that only hides stale instructions or produces ineffective compression.
If neither preparation arm meets acceptance, drop the optimization as specified
by the roadmap rather than relax commit or recovery guarantees.
