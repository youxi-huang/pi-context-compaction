# v0.5.0 note-quality plan

Status: design accepted by the maintainer on 2026-10-16. W0.1, W0.2, W1, W2 and
W3 are implemented and checked offline. The W0.3 baseline and W4 ran on DeepSeek
on 2026-10-16 within the approved envelope; four gates are met and the retrieval
gate is not (see [Gate results](#gate-results-on-the-first-provider-run)).
The plan covers both halves of the 0.5.0 milestone in the
[roadmap](roadmap.md#planned-minor-releases): fewer notes refused for quotation
errors, and retrieval that needs fewer `context_history` calls. It does not
authorize a provider run, a release, or a change to the resident fingerprint or
evaluation pin. Each of those waits for the maintainer, as set out below.

## What the evidence says

Both bounded live runs lost a checkpoint to `CONTEXT_NOTE_QUOTE`. In the
[0.3 run](validation.md#03-measurement-bounded-live-validation-2026-09-22-utc)
the quotation existed verbatim in `f2-00181` while the fact cited other entries.
The [v0.4.3 DeepSeek run](validation.md#v043-bounded-provider-run-on-official-pi-130-with-deepseek-v41-flash-2026-10-16-utc)
records the refusal but not where, or whether, the quotation existed. The same
run had two `context_note` calls refused for quotation. Two runs are not a rate.

The code shows how a misattribution happens. The session writer, the default,
reads the conversation as its own provider prefix, where entry IDs never appear.
It learns the IDs only from a manifest at the end of the handover request. The
manifest gives each uncovered entry its role and its first 80 characters with
whitespace collapsed; when the window is tight that falls to 40 characters, then
to bare IDs. To cite a quotation, the model has to match text it read in full
against those openings. The fixed writer does not have this problem, since every
chunk carries its `entryId` beside the text.

The validator in `notes.ts` stops at the first failing item and does not say
which one it was, so nothing today can aim a repair at the fault. The preview's
`readCandidate` runs the quotation check before the size check, so a quotation
failure never reaches the existing size repair.

Retrieval is a literal scan of the current branch, with Chinese split into
two-character terms. Speed is not the problem: on a synthetic branch of one
million estimated tokens, one query took about 30 to 40 ms in a cloud container,
mostly snapshot cloning and hashing. What the scan cannot do is answer "which
decisions about the timeout were made, and which one holds" in one call. The note
already has that structure. Its `instructions`, `reasons`, `failedPaths`, `files`
and `nextSteps` sections are the constraint, decision, failed-approach, file and
plan types; every item carries source IDs; `supersedes` records revisions. Older
checkpoints on the branch keep facts the newest note may have dropped.

The frozen evaluation cannot judge these changes. F1 and F2 each contain one
decision with a single correction. Nothing covers a value revised several times,
a withdrawn task, or an approach the user forbade retrying. The frozen runner
evaluates the resident runtime, and the preview has no paired recovery
measurement of its own. The v0.4.3 run answered 5 questions with 5
`context_history` calls and 9 questions with 11; that is one run, not a baseline.

## Decisions

Maintainer decisions, 2026-10-16:

| ID | Decision | Consequence |
| --- | --- | --- |
| N1 | 0.5.0 changes only the independent preview | New code lives under `preview/`. `notes.ts`, `history.ts`, `events.ts`, `config.ts` and `identity.ts` stay unchanged, so the resident `build.ts` fingerprint and the `eval/runtime.ts` pin do not move. The resident runtime keeps its v0.4 behavior; porting to it is a later, separate decision |
| N2 | At most one repair per compaction, for size or for quotation | The existing `noteRepair` setting (default on) governs both; there is no new setting. Quotation repair comes first when it applies, and a repaired note over the hard limit then blocks with `CONTEXT_NOTE_BUDGET`. Background preparation keeps repair off, as now |
| N3 | Provider measurements use DeepSeek V4.1 Flash, as in the v0.4.3 run | Each run's request, time and spending envelope is reported to the maintainer and approved before the first request |
| N4 | Quotation accuracy ships with 0.5.0 | No separate patch release. Both halves are judged on the same paired measurements |

Design rules this plan adopts:

| ID | Rule | Reason |
| --- | --- | --- |
| R1 | The host locates; the writer decides | The host never rebinds a quotation to another entry, not even a unique match. Text found only in an assistant message or a tool output would become a cited user ruling. The repair request shows each entry's role and leaves the choice to the writer |
| R2 | Repair asks only about the failing facts | Untouched facts are spliced back byte for byte. The repaired note passes the unchanged `validateNote` and the continuation check before commit |
| R3 | Stored formats stay as they are | No new checkpoint, note or marker field. v0.4.x checkpoints must open unchanged, and a v0.5.0 checkpoint must open in v0.4.3 |
| R4 | The typed view is computed on every call | It is derived from committed checkpoints and tool records in the current snapshot: no file, no database, nothing to go stale. Persisting it is a scope decision, taken only if measurement shows the need |
| R5 | A typed result returns originals | The writer's text appears only as a labelled summary; the evidence is the original excerpt. Results come from the frozen branch snapshot, so a hit never widens access |
| R6 | Measure before changing the writer | Diagnostics and the writer bench land first, and the baseline is recorded before W1 |

## Work packages

### W0 Diagnostics and the writer bench

**W0.1 Quotation diagnostics.** A pure function in `preview/quote-diagnostics.ts`
walks a parsed candidate the way `validateNoteContent` does, but collects every
failing quotation instead of stopping at the first. For each it records the
section and index, the cited IDs, up to five readable entries that contain the
quotation exactly (with their roles), and one class:

- `elsewhere`: the exact text is in another readable entry, as in the 0.3 run.
- `format`: no exact match, but a match after NFKC normalization and whitespace
  collapsing, in a cited entry or another one.
- `absent`: no readable entry contains it, so it is a paraphrase, a truncation or
  an invention.

It also reports whether any `sources` or `supersedes` ID is unreadable, which
makes the note ineligible for quotation repair. The function decides eligibility
and builds prompts and messages; it never accepts a note. Acceptance stays with
the unchanged validator.

`CONTEXT_NOTE_QUOTE` keeps its code. Its message adds the count per class and
whether a repair was attempted, never quotation text. The failure marker still
stores only the code.

**W0.2 Writer bench**, `scripts/context-memory-preview-bench.mjs`. It
installs a built preview package into official Pi the way stock acceptance does,
opens a fresh copy of a fixed session for every attempt, runs `/compact` through
RPC and records outcome, error code, diagnostic counts, writer calls, reported
usage and elapsed time. Sessions come from the W3 generator, so no real
conversation is used, and the output holds only counts and timings. Without a
provider flag it runs against a scripted loopback provider and checks the
harness. With `--provider deepseek` it requires explicit request and time limits
and stops at either one.

**W0.3 Baseline.** The baseline build is the preview with W0.1 alone: v0.4.3
behavior plus classified error messages, so baseline failures can be counted by
class. Once the maintainer approves the envelope (N3), the bench runs this build
on fixed cuts of the W3 sessions, and the W3 probes run on it once. The proposal
is three cuts per fixture with eight attempts each; the envelope sets the final
numbers. The record covers first-pass refusals by class, pause, writer cost,
accuracy per component and calls per question.

Completion: diagnostics and bench merged with offline regressions, and the
baseline recorded in `validation.md` as provider evidence with denominators.

### W1 Quotation accuracy

**W1.1 Quotable originals.** The session writer's handover request gains a block
listing every user message among the uncovered entries in full, one JSON object
each with `entryId` and text, in conversation order. Messages are included whole
or not at all, since a cut text invites a cut quotation. The block has its own
bound, proposed at the note's hard allowance. When the window is tight the block
is dropped before the manifest shrinks. The manifest header changes to say its
openings are for locating entries and must not be copied as quotations. Active
requests already appear with their IDs and are not repeated. The fixed writer is
unchanged.

The rules already ask the writer to "quote decisive user rulings verbatim", and
in coding sessions user messages are short next to tool output. The block sits in
the closing message, outside the cached prefix, so its tokens are paid at the
uncached rate. The bench reports them.

**W1.2 Targeted repair.** A repair runs when all of these hold: the candidate
fails only on quotations; at most five facts fail; `noteRepair` is on; and the
compaction's one repair is unused (N2). The writer then receives one request
without the session prefix, like the size repair: `cacheRetention: "none"`, no
tools, and the same 64,000-token ceiling. For each failing fact the request
carries:

- the section, the index and the complete fact;
- its class from W0.1;
- each cited entry's role and a bounded excerpt;
- each entry that contains the exact text, with its role and an excerpt around
  the match.

The request asks for exactly one replacement per listed fact, of three kinds:

- the same fact, citing an entry that contains the quotation;
- the fact without `quote`, when its cited sources support it without a verbatim
  ruling;
- `null`, which drops the fact.

It states that text found only in assistant or tool output is not a user ruling.
The response must cover each listed position once and nothing else.

The host then:

1. splices the replacements in and removes dropped facts;
2. runs `oneLineNote(validateNoteContent(...))`, the continuation check and the
   budget check.

Any failure blocks as it does today, including a second quotation failure.

The call is journaled with phase `repair`. The preview's progress record adds the
repair kind and counts dropped facts and removed quotations, so the bench can see
what the repair cost the note. Both fields stay local to the preview, because
`WriterCallRecord` belongs to the shared `events.ts`. R2 guarantees nothing else
changed.

**W1.3 Work-note feedback.** When `context_note` is refused with
`CONTEXT_NOTE_QUOTE`, the tool error uses W0.1 to name each failing field, plus
the IDs and roles of the entries that do contain the text. The model already
retries refused notes on its own, so this costs no extra call.

Regressions, in `packages/coding-agent/test/context-memory-preview-quote.test.ts`:

- each diagnostic class;
- a successful repair for each class;
- untouched facts stay byte-identical;
- a repaired note that fails again blocks;
- no repair when an ID is unreadable or more than five facts fail;
- `noteRepair: false` blocks without a call;
- only one repair across quotation and size;
- fixed-writer chunks;
- cancellation during repair;
- the quotable block's whole-message rule and shrink order;
- a v0.4.3 checkpoint reopens, and a new checkpoint keeps the stored format.

Completion: these regressions pass, and strict stock-Pi acceptance and scenarios
pass on Pi 1.1.0, 1.2.0 and 1.3.0.

### W2 Typed retrieval

The preview's `context_history` gains `operation: "list"`, with a required `kind`
and the optional `query`. Search and read pass through to `queryHistory`
unchanged. `list` is answered by `preview/history-view.ts`, from the same
`freezeHistory` snapshot, after `assertReady`.

| Kind | Source |
| --- | --- |
| `instructions`, `reasons`, `failedPaths`, `files`, `nextSteps`, `state` | Facts of every committed context-memory checkpoint on the branch |
| `edits` | `edit` and `write` tool calls with their `path`, marked failed when the paired tool result has `isError` |
| `errors` | Tool results with `isError`, and shell executions with a nonzero exit code |

The kinds reuse the note's section names, so the rendered note and the tool share
one vocabulary.

A note item carries:

- its source entries, with role and branch position;
- its `supersedes` IDs;
- `supersededBy`: the sources of later facts whose `supersedes` names one of its
  sources;
- the writer's text, labelled as a summary;
- an excerpt of its newest source around the query terms.

A fact repeated across checkpoints appears once, in the latest checkpoint's
wording. Items run newest first by source position. Pages use the same
4,000-token bound as search. The cursor is bound to the snapshot, the kind, the
query and a view version. Work-note candidates are not listed: they are
unverified, and their originals are still in context.

The tool description says the list comes from earlier checkpoints and tool
records, can miss what a writer left out, and that search remains the way to
check. Query terms follow the existing search rules. `searchTerms` is private to
`history.ts` (N1), so the preview carries its own copy, tested against the same
cases.

Regressions, in `context-memory-preview-history-view.test.ts`:

- each kind;
- superseded marks across three revisions, including a revert;
- deduplication across checkpoints;
- scope: entries off the branch are never listed, including after `/tree`;
- cursor misuse;
- the page bound;
- a branch with no checkpoints;
- the cost of one call on the largest session the failure store accepts (250,000
  entries), reported rather than asserted.

Completion: the regressions and strict stock-Pi acceptance pass, and the measured
per-call cost is recorded. If it exceeds 200 ms on the largest supported session,
the maintainer decides whether to persist the view (R4).

### W3 Preview evaluation set

A new set lives under `eval/preview/`, outside the frozen `eval/fixtures/`. It has
its own schema and scorer versions, `0.5-preview-fixtures.1` and
`0.5-preview-scorer.1`, and a deterministic generator with a hash manifest. The
frozen `eval/schema.ts` restricts fixture IDs to F1 through F3, so the new set
imports what it can reuse and defines the rest. Every record is invented. The
sessions are generated rather than driven by a model, so only writer calls and
probe answers use the provider.

There are at least two fixtures, each with three or more checkpoints:

- A coding task with five features:
  - a setting revised three times and finally reverted;
  - a subtask that is withdrawn;
  - an approach that fails, after which the user forbids retrying it;
  - a constraint from the second turn that matters after the third checkpoint;
  - a user ruling echoed verbatim by the assistant and again inside a tool
    output.
- A task like the v0.4.3 stock report, with decisions and errors among long tool
  outputs.

Probe kinds follow the [evaluation contract](roadmap.md#evaluation-contract):

- facts and exact values;
- source support;
- the current ruling and what it superseded;
- authority;
- continuation, including whether a forbidden approach is retried;
- questions whose answer is absent.

Every probe runs twice, once with `context_history` and once without, so what the
note carried and what retrieval found are reported separately. Probe prompts
never name the probe kind, and the runner passes no category to the runtime.

Each build's report gives:

- accuracy per component, with denominators;
- abstentions and unsupported claims;
- `context_history` calls per question, by operation;
- how often a forbidden approach is repeated;
- missed-entry probes, whose answers sit in entries no checkpoint cites.

Completion: the generator, scorer and scripted runner pass offline in CI.
Provider runs follow N3.

| Repair cost | Recorded. Three repairs, all committed; repaired attempts took 14.4 to 23.0 s against a 12.6 s median; no fact dropped and no quotation removed |
| Retrieval | Not met. Calls per question 1.36 against 1.40 over two runs each. With `context_history`, the strict scorer passed 87 of 94 against 92 of 94; read for content, 91 against 93. The content gap was the next-step finding, corrected in `f768030` and re-measured on P2 alone (17 of 17) |
| Coverage | Reported. One probe per run had an answer no checkpoint cites; it passed in every run but the candidate's second |

Four things stood between this and a release decision, each the maintainer's; the fourth is settled:

1. The corrected candidate has not run the full writer bench or P1's probes. A
   rerun of both, with two probe runs, needs about 320 requests and $1 at catalog
   prices.
2. Nine answers were scored incorrect for prose in the value field, two from the
   baseline and seven from the candidate. Before the next run, either the answer
   contract asks for a JSON boolean in so many words or the scorer counts prose
   values separately; the choice applies to both builds.
3. With no tools, the notes alone answered 184 of 188 probes by content, so P1 and
   P2 cannot show whether the typed list saves calls. That needs a fixture whose
   answers a note cannot hold.
4. Decided and done (`a2c62fa`): the session writer keeps the session's tools and
   sets no tool choice, for release as for measurement. With `tool_choice: "none"`,
   DeepSeek left the tools out of the prompt and the writer paid for the whole
   history on every compaction; now 91 to 99.6% of its input came from cache in a
   check and each call cost about a third. The full rerun in item 1 should count
   tool calls during the handover, which refuse the note; the check saw none in
   six. The bench reproduces a session's cache state by default.

## Deferred and out of scope

**Stable fact identities, deferred.** v0.4.1 left `supersedes` pointing at entries
rather than facts, with accumulated facts growing toward the schema's bounds. A
host-assigned fact ID would let a revision name the fact it replaces and let the
view follow one fact across checkpoints. It changes the stored note, so it needs a
compatibility plan. 0.5.0 writes only the design. Implementation follows if W3
shows superseded rulings as a main source of lost accuracy. Of Graphiti's model,
the provenance lists and expired-but-kept facts apply. Its second timeline does
not: a ruling in a session takes effect at its position on the branch.

**Out of scope for 0.5.0:**

- SQLite and FTS5, embeddings, vector stores and graph stores. Three reasons:
  `node:sqlite` is still experimental on Node 22, which the preview supports; an
  FTS table that stores text is a second copy of history; and the trigram
  tokenizer does not index two-character Chinese terms.
- Rewriting accumulated observations in the style of Mastra's reflector, which
  would replace source-linked facts with unchecked summaries.
- Cross-task experience memory such as ReasoningBank, which the roadmap places
  outside this project.
- Model-judged support checks in the compaction path. RAGChecker-style judging of
  individual claims may be used offline on small samples, never as a commit gate.

## Open points, settled during implementation

The maintainer left these to implementation:

- **The quotable block's bound:** the note's hard allowance, measured like
  the note. When messages overflow it, the newest are kept: a later ruling
  overrides an earlier one, and the previous note already carries earlier
  quotations. A message that does not fit is left out whole.
- **The limit for a repair:** five failing facts. Above that, the fault lies
  in the whole note rather than a few bindings, and the note blocks.
- **How the bench sees a repair:** `/compaction-status` already reports each
  call's phase under `lastWriter`; the earlier note that it did not was
  wrong. 0.5.0 adds the repair kind, the first-pass quotation classes and the
  repair's outcome to the same record.
- **How a probe withholds `context_history`:** the runner calls Pi's public
  `setActiveToolsByName` with only `context_history` for one condition and
  with no tools for the other. Nothing else in the request changes; the
  runner records the active tools of every probe.
