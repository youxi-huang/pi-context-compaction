# v0.7.0 host-neutral core plan

Status: accepted and executed. The maintainer took H1 to H7 as proposed on
2026-10-22 and the milestone landed the same day; the evidence is the 0.7.0
entry in [validation.md](validation.md). Nothing
in this plan authorizes a release, a provider run, a change to the resident
fingerprint or the evaluation pin, or the project's rename, which is a separate
decision settled before the first adapter for a host other than Pi ships. The
plan covers the 0.7.0 milestone in the
[roadmap](roadmap.md#planned-minor-releases), whose entry is the binding
authority for scope and acceptance: can the method be stated and run without
Pi? The release writes the specification, moves the preview's host-independent
logic into a core package in this monorepo that imports nothing from Pi, makes
the Pi extension the core's first adapter with no change in behavior, gives
validation conformance vectors and the fixtures a host-neutral record format,
and freezes the resident runtime. The guarantees stay stated in terms of
records, branches, checkpoints and a commit gate, as the
[architectural direction](roadmap.md#architectural-direction) has them; this
plan is how the code comes to match that statement.

## What the source says

The host-independent logic already exists; what binds it to Pi is two kinds of
import. Value imports carry lifecycle, transport, file IO and UI and belong to
the adapter. Type imports — `SessionEntry`, `SessionProjection`,
`AgentMessage`, `ThinkingLevel` — carry only shapes, and the lift replaces them
with structural record types the specification defines. The proof that this
works is already merged: `preview/reduction.ts` is a pure function of the
branch's records and the model's declared cache lifetime, typed against its own
minimal `ReductionRecord` shapes, importing nothing but the shared
`identity.ts`; its module comment records that v0.6.0's rule G1 shaped it so
0.7.0 can lift it unchanged. It is the first lift and the pattern for every
other one.

The five shared files the preview bundles (`config.ts`, `events.ts`,
`history.ts`, `identity.ts`, `notes.ts`) are the same split in miniature.
`identity.ts` is already pure and holds `hashEntries` and `hashEntryPrefixes`,
whose bytes every stored checkpoint's source snapshot depends on. `notes.ts`
(schema, validation, rendering, lineage) and `history.ts` (`queryHistory`,
snapshot and page types) import only the `SessionEntry` type from the host and
retype cleanly; `history.ts` also carries `freezeHistory` and the parent-grant
machinery, which read the host's session manager and stay host-side — grants
are resident-only and the preview does not support them. `config.ts` splits
into note budgets, `textTokens` and `memoryBudget` (core) against
`readMemoryConfig`'s file reading and model typing (adapter). `events.ts`
splits into the event and usage record types, `PROJECT_CODES` and `errorCode`
(core contracts) against the `EventLog` file IO (resident-only).

Three facts about identity make the lift safe to sequence:

- The resident fingerprint (`scripts/stamp-context-memory.mjs`) hashes the six
  host files, `overflow.ts` and the top-level `.ts` files of the extension
  directory only — `readdirSync` does not descend into `preview/`. Preview
  modules can therefore move into the core freely; the five shared top-level
  files must stay in place byte for byte, which is why the roadmap has the core
  start from copies of them.
- The preview builder already enforces the needed check in one direction: it
  rejects any bundled input outside `preview/` and the five shared files
  ("Preview must not bundle host or resident lifecycle code") and any external
  import beyond `node:`, the Pi peers and TypeBox. The new `verify` check for
  the core is this allowlist with the Pi peers removed.
- Refusals are already classes, not text: `PROJECT_CODES` in `events.ts` is a
  closed set, and `errorCode` reduces any message to one of them. Conformance
  vectors can therefore match outcomes mechanically.

What 0.6.0 leaves open, which this plan sequences around rather than waits for:
the reductions, excerpts, history-view pricing and the token-overhead report
are implemented offline and lift as they stand; the provider benches (M3, M4
and the WP0 channel), the deferred decisions M5 to M8 and the rendered-note
projection of its WP3 (no `context-memory-preview-render.test.ts` exists yet)
remain open on their own track.

The evaluation side: `eval/preview/generate.ts` writes Pi version-3 sessions
directly, pinned byte-for-byte by the fixture manifests. The
[evaluation contract](roadmap.md#evaluation-contract) says that from 0.7.0
fixtures use a host-neutral record format which each host's runner converts
into that host's sessions, and the roadmap's acceptance requires the P1 to P3
offline results to reproduce.

## Decisions

Proposed to the maintainer; none is taken by this plan:

| ID | Proposal | Consequence |
| --- | --- | --- |
| H1 | The core package's location and working name in this monorepo | Proposed: `packages/compaction-core`, private and unpublished, with a host-neutral name that contains no `pi`. The project's future name is settled (SLICE, the maintainer's decision of 2026-10-22, recorded in the roadmap), so `packages/slice-core` is equally open; the rename itself still lands with the first non-Pi adapter, and stored identifiers such as `context-memory` and `pi-context-memory.json` keep their names, as the roadmap settles. The maintainer picks the directory and manifest name |
| H2 | The canonical serialization the specification defines for hosts other than Pi | Proposed: RFC 8785 (JCS) canonical JSON of each record's normalized form, framed per entry with the same newline byte `hashEntries` uses, SHA-256 over the sequence. It binds every future adapter from its first release, so the choice is the maintainer's. Pi keeps `hashEntries` byte-compatibly, and migrating Pi to the canonical form remains the unassigned source-hash follow-up with its own compatibility plan |
| H3 | Where the conformance vectors live and how they are versioned | Proposed: `conformance/` inside the core package, pinned by a SHA-256 manifest as the fixture sets are, versioned `0.7-conformance.1`. 0.10.0 publishes the validator together with the vectors as a package, so they live beside the validator from the start |
| H4 | Where the specification lives | Proposed: inside the core package (`spec/`), so the 0.10.0 repository split carries it with the code it governs, with `docs/context-memory/` keeping a pointer. The alternative is `docs/context-memory/spec.md` until the split |
| H5 | What the resident freeze permits | The roadmap freezes the resident from this release: no further Pi ports and no new features, tags and history retained, retirement by 0.10.0 once the P-series fixtures cover what the F-series measured. Proposed reading: dependency and security maintenance under [operations.md](operations.md) continues until retirement; feature work and host-version ports stop. The maintainer confirms the boundary |
| H6 | How the fixtures gain the host-neutral record format | Proposed: `generate.ts` emits host-neutral records, and the Pi converter must reproduce the pinned P1 to P4 fixture bytes hash for hash, checked against the existing manifests, so the frozen offline baselines carry over without re-pinning. The alternative — regenerating and re-pinning the fixtures — moves frozen inputs and is not proposed |
| H7 | The error classes' names in the specification | Proposed: the `CONTEXT_` and `HISTORY_` codes of `PROJECT_CODES` are declared stable identifiers of the specification, unchanged by the future project rename, because behavior identity and the conformance vectors both match on them. Renaming codes later would be a breaking specification change; the maintainer confirms before the spec freezes them |

Design rules this plan adopts:

| ID | Rule | Reason |
| --- | --- | --- |
| K1 | The core imports nothing from Pi, type-only imports included | Records are typed structurally after `reduction.ts`'s pattern; the core's only library dependency is TypeBox plus `node:` builtins without file or network IO in core logic. `verify` gains a check that rejects any `@earendil-works/*` or host-source specifier in the core, modeled on the preview builder's input allowlist |
| K2 | A lift is copy, retype, re-import — never a behavior change | For the same scripted inputs the Pi extension produces the same notes, the same citations and the same error classes, and every existing preview regression and scenario passes unchanged against the lifted modules. A lift that needs a behavior change is wrong or is not a lift |
| K3 | Stored formats stay as they are | The Pi adapter keeps `hashEntries` and `hashEntryPrefixes` byte-compatibly, the stored checkpoint rendering byte for byte, and writes no host or adapter field, so Pi checkpoints keep their format and still open in earlier versions; v0.4.x and v0.5.x checkpoints reopen |
| K4 | The record model keeps the host's native record beside its normalized text, and a tool call and its result are one unit | An adapter can always return the host's own payload; the core never invents a record ID and cites only the host's own IDs |
| K5 | The core keeps no copy of history | Original records stay in the host's storage; every core view is computed on demand or disposable, as the reductions and the typed list already are |
| K6 | The writer contract is core; the transport is the adapter's | Schema, rules, quotable text, repair and accounting are shared. Dispatch, model resolution, reasoning mapping and the session-ID `prompt_cache_key` stay with the adapter, because cache reuse depends on reproducing the host's own request, as the 0.5.0 cache fix showed |
| K7 | Commit checks are deterministic; the host locates and the writer decides | No model decides a commit, and no adapter rebinds a quotation to another record. v0.5.0's R1 and the roadmap's adapter rules enter the specification verbatim |
| K8 | One lift at a time, in the stated order, each behind the full offline acceptance | Reduction first, then validation and repairs, then formats, then views and accounting, then the writer-contract split. Every intermediate state builds and passes strict stock-Pi acceptance, so a fault is attributable to one lift |
| K9 | The resident runtime and both deliberate gates do not move | The core starts from copies of the five shared files; the shared files, the resident `build.ts` fingerprint and the `eval/runtime.ts` pin stay byte-identical. The duplication is deliberate and bounded by the freeze: the resident retires by 0.10.0, and no fix is ported into it meanwhile under H5 |
| K10 | No 0.6.0 decision is taken by the lift | Switch names, defaults, tiers, bounds and report columns carry exactly as they are. A deferred M-decision taken later lands once, in the core, never in two copies |
| K11 | Segments are not built; their seams are left open | `preparation-candidate.ts` lifts as it stands, and the specification states the coverage rules a checkpoint already obeys (it covers what its candidate or notes saw; every later original stays verbatim), so 0.8.0 can add segment preparation and a merge under the full commit checks without changing the contract. Nothing more is added for them |
| K12 | Conformance matches error classes from the closed set, never message text, and vectors carry only invented content | Message wording may improve without breaking conformance; no session log, credential or local path can enter a vector |

## Work packages

### WP0 The specification

One document (home under H4) that states the method without naming Pi, each
guarantee beside the check that enforces it and the error class a violation
raises. Its sections:

- **The record model.** A record carries the host's ID, the host's native
  payload (opaque to the core), its normalized text, role, kind and timestamp;
  a tool call and its result form one unit that is never split, as Better
  Compact's adapters have it and as `assertToolPairs` and reduction rule G5
  already enforce. Branches are ordered record sequences; the core computes
  only over what it is given and invents no ID (K4).
- **The note format.** The six fact sections and open questions of
  `noteSchema`, one line per fact, sources required on every fact, optional
  verbatim `quote` and `supersedes`, the schema's bounds, and the two
  removable answer envelopes of `note-envelope.ts` with the rule that nothing
  else is ever rewritten.
- **The checkpoint format.** The committed note, the source snapshot with its
  hash, the first kept record, lineage, and the preview's preparation
  metadata; the coverage rules of K11. The stored rendering is the adapter's
  (Pi keeps its bytes, K3); the derived projection is the core's.
- **The source hash, by its properties.** Deterministic for the same records;
  changed when cited content changes under the same ID; prefix hashes share
  the exact bytes of the whole-sequence hash. The Pi adapter satisfies it with
  `hashEntries` over native entries, byte-compatible with every stored
  checkpoint; every other host uses the canonical serialization of H2 from its
  first release. Citations alone do not detect changed content under the same
  ID, which is why the hash exists.
- **Validation and the commit gate.** The pipeline in order: parse, envelope
  removal, schema (`CONTEXT_NOTE_INVALID`), citation scope
  (`CONTEXT_NOTE_SCOPE`), quotation (`CONTEXT_NOTE_QUOTE`), budget
  (`CONTEXT_NOTE_BUDGET`), continuation (`CONTEXT_CONTINUATION_MISSING`);
  the bounded repairs — at most one per compaction, quotation before size,
  sources-only and splice-only, `CONTEXT_NOTE_REPAIR_LOSS` on any loss — and
  the deterministic rule that the host locates and the writer decides (K7).
- **Commit and failure states.** Pending, staged, committed, blocked; durable
  markers that carry identifiers and classes, never content; a failed
  compaction blocks the next request at the Gated level, explicit retry and
  recovery confirm a validated checkpoint on disk before requests resume, and
  no adapter falls back silently. The guarantee-level table (Gated, Checked,
  Traceable) enters the specification from the roadmap unchanged.
- **Retrieval.** Search, read and the typed list over the current branch's
  frozen snapshot; page bounds; results are original excerpts so a hit never
  widens scope; `readTokens`, low detail and `inContext` marks as the 0.6.0
  candidates define them; reductions and excerpts as derived, deterministic
  views (G1 to G10 of the [v0.6.0 plan](v0.6.0-plan.md) restated as core
  obligations).
- **Call accounting.** Usage fields, phases and purposes; a call without a
  usage report is unknown, never free; `writerContractHashes` binds a journal
  to the contract that produced its calls.
- **The guarantee table.** For each guarantee the enforcing check and class,
  for example: citation scope — `validateNoteContent` — `CONTEXT_NOTE_SCOPE`;
  quotation integrity — the quotation check — `CONTEXT_NOTE_QUOTE`; unchanged
  sources at commit — snapshot hash comparison and disk readback —
  `CONTEXT_SOURCE_CHANGED`; tool pairing — `assertToolPairs` —
  `CONTEXT_TOOL_BOUNDARY`; blocked continuation — the request guard —
  `CONTEXT_BLOCKED`. The full table is the deliverable; a guarantee without a
  named, existing check does not go in it.

Completion: the document exists, every guarantee row names a check that exists
in the core with its class from `PROJECT_CODES`, and the maintainer has
reviewed it. The conformance vectors of WP3 are its mechanical form.

### WP1 The core package and the import gate

Create the package (H1) seeded with copies of the five shared files, retyped
against the specification's structural record shapes — `notes.ts` and
`history.ts` lose their `core/session-manager.ts` type import, `config.ts`
keeps the budget and token logic and leaves settings reading behind,
`events.ts` keeps the contracts and leaves `EventLog` behind, `identity.ts`
copies unchanged. The package's manifest declares TypeBox as its only
dependency; its own tests run under the repository's runner but import nothing
from Pi.

Two checks land with the scaffold:

- `verify` (through `scripts/context-memory-check.mjs`) gains the host-import
  gate: every import specifier reachable from the core package must be
  relative within the package, `node:`, or `typebox`; anything else — any
  `@earendil-works/*`, any path into `packages/coding-agent/src` — fails, in
  type position too. A deliberately planted host import is the check's own
  regression.
- An isolation check, in the manner of the stock-Pi acceptance's temporary
  directories: the core is built and its tests run in a directory where no
  `@earendil-works/*` package resolves, which is the roadmap's "builds and
  tests without Pi packages" made mechanical.

Regressions: the copied files keep their existing focused coverage, cloned to
the core's test directory and retargeted; the resident's tests keep running
against the resident copies untouched (K9).

Completion: the package builds, its tests pass in isolation, the import gate
runs in `verify` and CI, and `doctor` reports the new layout.

### WP2 The lifts

In K8's order, each step moving modules into the core, retyping their record
parameters, and re-importing them from the preview so the Pi extension's
behavior is unchanged:

1. **Reduction.** `reduction.ts` moves unchanged; `controller.ts` imports it
   from the core. The first lift proves the path end to end.
2. **Validation and repairs.** `schema-diagnostics.ts`,
   `scope-diagnostics.ts`, `quote-diagnostics.ts`, `quote-repair.ts`,
   `sources-repair.ts`, `note-envelope.ts`.
3. **Formats.** The seeded `notes.ts` becomes the one the preview uses; the
   work-note schema and merge of `work-notes.ts`; the checkpoint and
   preparation metadata shapes of `contracts.ts` (its Pi-typed store contract
   stays in the preview).
4. **Views and accounting.** The typed list, pricing and low detail of
   `history-view.ts`; the excerpt selection and secret filter of
   `excerpts.ts` (settings reading stays); the accounting contracts of
   `call-journal.ts` (journal IO stays); `preparation-candidate.ts` whole
   (K11); the controller's pure helpers.
5. **The writer-contract split.** Rules text, manifest construction,
   `quotableOriginals`, candidate reading with envelope removal, the
   diagnostics-and-repair sequencing, `sumMemoryUsage` and
   `writerContractHashes` move to the core; `resolveWriterModel`, dispatch,
   reasoning mapping and `prompt_cache_key` stay in the preview as the Pi
   transport (K6).

The preview builder's `shared` allowlist becomes the core package: the bundle
may contain preview files and core files, nothing else, and its external
imports stay `node:`, the Pi peers and TypeBox. The preview's own source
fingerprint changes with every candidate as it always has; the resident
fingerprint does not move, because `preview/` was never in it and the five
shared top-level files keep their bytes (K9).

Regressions, each lift step green before the next starts:

- every existing `test/context-memory-preview-*.test.ts` and the stock-Pi
  scenarios pass unchanged (K2);
- an equivalence run: the scenario and loopback-bench inputs produce
  byte-identical notes, citations and error classes on the pre-lift and
  post-lift packages, compared mechanically;
- cross-open both ways, as 0.5.0's R3 checked: a chain of checkpoints written
  by the lifted package opens, validates and continues under the released
  v0.5.3 package, and the reverse (K3).

Completion: no file under `preview/` contains logic the classification table
marks core; strict stock-Pi acceptance passes on Pi 1.3.0, 1.2.0 and 1.1.0.

### WP3 Conformance vectors and the host-neutral fixtures

**Vectors** (home and version under H3): each vector is a set of host-neutral
records plus a candidate note, with the expected outcome — commit, or refusal
with one error class (K12). The set covers at least: a valid note; facts
without sources; scope misses, missing and unreadable separately, including in
`supersedes`; the three quotation classes `elsewhere`, `format` and `absent`;
budget overflow at the tier boundaries; both answer envelopes and their near
misses; a repair that drops what it may not (`CONTEXT_NOTE_REPAIR_LOSS`); an
unpaired tool call; a continuation left out; and cited content changed under
the same record ID, which the source hash must catch under both serializations
(the Pi adapter's `hashEntries` and H2's canonical form). Every implementation
must accept, or refuse with the same class; the core's validator runs them
directly, and the Pi adapter runs them through the fixture converter below, so
both paths are checked to agree. All content is invented.

**Fixtures**: `eval/preview/generate.ts` emits the host-neutral record format,
and a converter renders Pi version-3 sessions from it. Under H6 the converted
bytes must equal the pinned P1 to P4 fixtures hash for hash against the
existing manifests, so the frozen offline baselines and the manifests do not
move, and `--check` keeps failing on any byte difference. The frozen F-series
under `eval/fixtures/` is untouched: it evaluates the resident runtime and
retires with it.

Regressions: a vector runner in the core's tests; a preview test running every
vector through the Pi adapter path; the converter byte-identity check beside
the generator's existing `--check`.

Completion: vectors versioned and green on both paths; converter identity
green in CI.

### WP4 Adapter acceptance and the freeze

The Pi extension, now built on the core, re-earns every promise of the
[preview guide](extension-preview.md) unchanged — same install lines, same
supported hosts, same behavior:

- strict stock-Pi acceptance and the scenario suite on every listed Pi
  version (1.3.0, 1.2.0, 1.1.0), with the long-session request-overhead
  target;
- v0.4.x and v0.5.x checkpoints reopen, and the cross-open regression of WP2
  holds on the release candidate;
- the P1 to P3 offline results reproduce: the loopback writer bench and probe
  runs match the recorded offline baselines, and the token-overhead report's
  arithmetic regressions pass.

The resident freeze is recorded where readers will meet it — a dated paragraph
in [upstream-delta.md](upstream-delta.md) and a line in the preview guide —
stating H5's boundary: no further Pi ports, no new features, maintenance per
the maintainer's confirmation, retirement by 0.10.0 once the P-series covers
what the F-series measured. Mapping that coverage is 0.9.0/0.10.0 work, not
this release's. `CHANGELOG.md` records the release under **Unreleased**;
the documentation calls the extension the core's first adapter from here on.

Completion: all gates below green on one commit, entirely offline.

## Dependencies and room left

**On 0.6.0's unfinished pieces.** The lift carries current behavior, whatever
its switch defaults (K10). The provider benches (M3, M4 and the measurement
channel), the deferred decisions M5 to M8 and the rendered-note projection of
0.6.0's WP3 are not prerequisites and are not waited for: a decision taken
after the lift lands once, in the core. The rendering projection, when built,
is a pure projection over the stored note and lineage and belongs in the core
by construction; building it before or after the lift changes only where it
lands, so it should land after.

**For 0.8.0.** Segments are written once, in the core, after this release —
this plan leaves their seams open without building them (K11). Concretely: the
candidate lifecycle of `preparation-candidate.ts` and the prefix-commit rules
live in the core with records in and validated candidates out; the
specification states checkpoint coverage so a boundary that merges validated
segments under the full commit checks slots in without a format change; call
accounting already separates `preparation` from `compaction` phases, which the
interval caps and breaker of 0.8.0 will read. The merge itself, stable fact
identities, segment triggers and budgets are 0.8.0's and do not appear here.

**For 0.9.0 and 0.10.0.** The second host is judged against the conformance
vectors and the guarantee-level table, which is why both are core artifacts
matched by class rather than text (K12, H3). The repository split takes the
core package, its spec and its vectors whole, so the core's imports stay
package-relative and nothing in it reads a path outside itself.

## Deferred and out of scope

- **No second host.** The capability review and the second adapter are 0.9.0;
  dsh, which attaches the way Pi does, may follow any time after 0.7.0 but is
  no part of it, and the project rename it requires is likewise not this
  release's.
- **No repository split and no published package.** The core lives in this
  monorepo until 0.10.0; the validator-and-vectors package is 0.10.0's.
- **No behavior change anywhere.** Not in notes, citations, error classes,
  budgets, repairs, reductions, retrieval or rendering (K2); a cleanup that
  changes bytes on the scripted inputs fails the identity gate.
- **No migration of Pi's stored checkpoints to the canonical serialization.**
  Pi keeps `hashEntries`; the move remains the unassigned source-hash
  follow-up with its own compatibility plan and its regressions that
  distinguish field reordering from changed content.
- **No provider calls in this release's acceptance**, and no new provider
  evaluation is authorized by this plan.
- **No new history store, no substitute writer, no weakened failure
  blocking.** The specification states these as obligations; the release
  changes no enforcement.
- **The resident runtime gains nothing.** No port of the preview's 0.5.x/0.6.x
  work into it; it is frozen under H5 and retires by 0.10.0.
- **Delegated retrieval, instruction authority, stable fact identities** keep
  their own releases, and the 0.5.0 exclusions (SQLite/FTS5, embeddings,
  reflector-style rewriting, cross-task memory) stand.

## Open points, left to implementation

- The structural record type's exact fields, settled against what the
  classified modules actually read (`reduction.ts`'s shapes, `sourceText` and
  `sourceRole`'s inputs) and recorded in the specification.
- How the equivalence run captures and compares its outputs — proposed: the
  scenario runner and loopback bench gain a mode that writes content hashes of
  notes, citations and classes per case, compared across two package builds.
- The split line inside `config.ts` and `events.ts`, settled so that the
  resident copies keep their bytes and the core halves import nothing back.
- The vector file format (records, candidate, expected class) and its
  manifest, settled with H3.

## Order

1. WP0's specification drafted beside WP1's scaffold; the spec is reviewed
   before the first retyped module lands, so retyping follows one record
   model.
2. WP1: the package, the import gate in `verify`, the isolation check.
3. WP2: the five lift steps in order, each behind the full offline
   acceptance, with the equivalence run from the first step on.
4. WP3: vectors and the fixture format with its converter.
5. WP4: adapter acceptance on all listed hosts, the freeze recorded, the
   changelog entry; then the release waits for the maintainer.
